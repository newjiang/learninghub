### Q1：访问跨网段服务器时 ARP 查谁？

> **一句话结论**：通常查路由选出的下一跳网关，而非直接查远端服务器。

**机制展开**：先最长前缀匹配路由，再在相应链路解析邻居；IP 目的保持远端，帧目的对应当前下一跳。

**具体推演**：192.0.2.10/24 去 198.51.100.20，经 192.0.2.1 时，先获取该网关的链路地址。

**⚖️ 方案对比与代价**：逐跳封装隔离链路技术，地址转换和隧道又会改变部分观察；不能只抓一侧推断全路径。

**🔎 追问演练**：ping 通但应用不通说明什么？

**推演要点**：仅证明特定探测路径可达，还要检查端口、握手、回程和应用策略。

**原理展开**：[计算机网络对应章节](计算机网络原理.md#p-02)。

<a id="q-02"></a>
### Q2：为什么小请求通，大响应卡？

> **一句话结论**：可能是路径 MTU、探测反馈、丢失或接收窗口问题，不能只归因带宽。

**机制展开**：隧道降低可用包大小，相关错误反馈被过滤可形成黑洞，证书大链也可能先暴露。

**具体推演**：先比较不同大小的受控探测，再结合双方抓包定位缺失与重传，注明网卡卸载。

**⚖️ 方案对比与代价**：分片便于适配但放大丢失和状态成本；单纯增大发送缓冲未必修复。

**🔎 追问演练**：本机抓到大于 MTU 的 TCP 包一定错误吗？

**推演要点**：不一定，抓包点可能看到卸载前分段或聚合后的形态。

**原理展开**：[计算机网络对应章节](计算机网络原理.md#p-03)。

<a id="q-03"></a>
### Q3：为什么三次握手，关闭却不总是四包？

> **一句话结论**：握手同步双向序号和确认能力，关闭独立结束两个方向，报文可以合并。

**机制展开**：SYN/FIN 各占序号，第三次确认让服务端知道自己的序号已被收到；FIN 不关闭反向全部数据。

**具体推演**：客户端 FIN 后仍可接收服务端剩余响应，ACK 与 FIN 可合并或发生同时关闭。

**⚖️ 方案对比与代价**：额外往返与状态换取可靠建立语义，但不认证业务身份，也不能独自防全部资源耗尽。

**🔎 追问演练**：TIME_WAIT 一定在客户端吗？

**推演要点**：看主动完成关闭等具体状态路径，服务端也可出现，不能按角色固定归属。

**原理展开**：[计算机网络对应章节](计算机网络原理.md#p-04)。

<a id="q-04"></a>
### Q4：TCP ACK 能否证明订单成功？

> **一句话结论**：不能，它至多证明相应字节到达对端传输层，不证明业务提交。

**机制展开**：发送接纳、线上传输、对端接收、应用读取与数据库提交是不同阶段。

**具体推演**：服务端提交后响应丢失，客户端仍超时；重发可能产生重复副作用。

**⚖️ 方案对比与代价**：TCP 可靠字节流降低传输重复与乱序负担，应用仍需幂等标识和结果确认。

**🔎 追问演练**：write 返回是否说明已上网？

**推演要点**：可能仅被本地缓冲接纳，应按接口与抓包证据区分层级。

**原理展开**：[计算机网络对应章节](计算机网络原理.md#p-05)。

<a id="q-05"></a>
### Q5：禁用 Nagle 能解决粘包吗？

> **一句话结论**：不能，TCP 字节流本来就不保留应用写入边界。

**机制展开**：分段、合并和接收缓冲使一次 read 与 write 不一一对应，协议必须显式封帧。

**具体推演**：一个长度头可能分两次收到，一次 read 也可能同时包含三帧，均需状态机。

**⚖️ 方案对比与代价**：Nagle 和延迟确认影响小包时延与效率，不能恢复消息边界。

**🔎 追问演练**：长度前缀只读出长度后直接分配可以吗？

**推演要点**：先验证上限和整数范围，再管理半帧、期限和全局内存预算。

**原理展开**：[计算机网络对应章节](计算机网络原理.md#p-05)。

<a id="q-06"></a>
### Q6：流量控制和拥塞控制有什么区别？

> **一句话结论**：前者保护接收端，后者约束网络在途压力。

**机制展开**：rwnd 与 cwnd 共同影响发送，拥塞算法根据反馈调整；窗口还要扣除已在途数据。

**具体推演**：接收端读慢可使窗口缩小；出口排队丢失却可能在接收端空闲时发生。

**⚖️ 方案对比与代价**：更大缓存可缓解突发却增加延迟，不能把持续超载变成更高服务能力。

**🔎 追问演练**：100Mbit/s、50ms 的在途量约多少？

**推演要点**：带宽时延积约 625KB，是理想估计，实际需考虑竞争、排队与协议开销。

**原理展开**：[计算机网络对应章节](计算机网络原理.md#p-06)。

<a id="q-07"></a>
### Q7：UDP 不可靠，QUIC 为什么可靠？

> **一句话结论**：UDP 只是承载，QUIC 自己定义确认、恢复、有序流与拥塞协调。

**机制展开**：QUIC 多流使一个流的数据缺口不必阻塞其他独立流交付，仍共享链路和拥塞资源。

**具体推演**：HTTP/2 的一个 TCP 字节缺口可拖住其他流，QUIC 对应流可独立推进。

**⚖️ 方案对比与代价**：减少跨流传输队首阻塞，却增加用户态调度、加密与 UDP 路径兼容成本。

**🔎 追问演练**：HTTP/3 是否完全没有队首阻塞？

**推演要点**：流内顺序、应用依赖和头压缩等仍可阻塞，不能绝对化。

**原理展开**：[计算机网络对应章节](计算机网络原理.md#p-07)。

<a id="q-08"></a>
### Q8：DNS 改记录后为什么不立即切流？

> **一句话结论**：多层正负缓存和实际客户端策略让旧结果继续存在。

**机制展开**：TTL 约束缓存有效时间，已有缓存不是权威改动后主动全球清除；递归、系统和连接复用还影响观察。

**具体推演**：新服务刚上线可能遇到先前不存在记录的负缓存，旧长连接也不需重新解析。

**⚖️ 方案对比与代价**：缓存减少延迟与权威负载，代价是切换不即时；计划迁移需预留重叠和回滚。

**🔎 追问演练**：加密 DNS 是否证明回答真实？

**推演要点**：它保护特定传输路径，权威数据认证、域名控制和业务 TLS 身份是不同层。

**原理展开**：[计算机网络对应章节](计算机网络原理.md#p-08)。

<a id="q-09"></a>
### Q9：no-cache 和 no-store 一样吗？

> **一句话结论**：不一样，前者通常要求重用前验证，后者表达不存储的指令。

**机制展开**：新鲜度、验证与变体决定缓存复用，ETag 及条件请求可避免传输未变化表示。

**具体推演**：缓存持有旧表示时验证得到 304，可重用相应内容，未必重新下载全量。

**⚖️ 方案对比与代价**：缓存降低带宽与延迟，但授权、Vary 和私有/共享规则错误可跨用户泄漏。

**🔎 追问演练**：幂等是否要求返回完全相同字节？

**推演要点**：不是，关注重复请求预期效应，返回时间、状态等可能不同。

**原理展开**：[计算机网络对应章节](计算机网络原理.md#p-09)。

<a id="q-10"></a>
### Q10：TLS 1.3 为什么既需要证书签名又需要 Finished？

> **一句话结论**：前者认证持钥者及相应握手上下文，后者确认派生密钥与握手记录。

**机制展开**：链和身份检查先决定公钥可否信任，握手签名证明相应私钥控制，密钥协商和记录加密另有角色。

**具体推演**：RSA 证书可签名认证，同时使用临时椭圆曲线协商与对称 AEAD 传数据。

**⚖️ 方案对比与代价**：分离角色有利前向安全和算法演进，但恢复、0-RTT 与元数据仍有边界。

**🔎 追问演练**：0-RTT 可以任意重放扣款吗？

**推演要点**：不能默认，早期数据有重放风险，需协议和业务级限制。

**原理展开**：[计算机网络对应章节](计算机网络原理.md#p-10)。
