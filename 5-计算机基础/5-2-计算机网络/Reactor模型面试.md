## Q1：Reactor 是什么？为什么它能用少量线程管理很多连接？

> **一句话结论**：它把大量连接的等待交给事件多路复用，再由事件循环分派就绪事件，不为每条空闲连接单独保留平台线程。

**按过程展开**：先区分等待与处理：一万连接中大部分无数据时，一个等待集合可以表示这些连接；有数据的连接被选出后，应用才推进 read、解码与业务。线程可以睡在统一等待点，但不应卡在某条无数据连接或某次慢业务里。少线程节省的是等待表达与部分调度资源，不是减少真实业务计算量。

**继续追问**：十万连接能否保证比一万线程更快？

**推导答案**：不能。还取决于活跃比例、消息大小、回调时间、内核与应用缓冲、CPU 和带宽。连接数量本身不是性能比较的完整负载。

**回到原理**：[对应章节](Reactor模型原理.md#p-01)。

<a id="q-02"></a>
## Q2：非阻塞、多路复用和异步是同一个意思吗？

> **一句话结论**：不是：非阻塞描述调用等待行为，多路复用描述一组事件的等待，异步操作接口描述提交与完成的分离。

**按过程展开**：非阻塞 read 可立即返回暂不可用，若反复扫描所有连接仍会浪费 CPU；多路复用让应用等到有连接可推进再处理；异步完成通知则可能在运行时执行完某次操作后回调。底层既可能是完成型机制，也可能由线程或就绪状态机实现。

**继续追问**：select 会阻塞，为什么还能叫非阻塞服务端？

**推导答案**：它阻塞在统一等待点，等待任意事件；各已连接 socket 的处理不会因某一条连接无数据而一直等待。两者并不冲突。

**回到原理**：[对应章节](Reactor模型原理.md#p-02)。

<a id="q-03"></a>
## Q3：可读通知为什么不等于一条请求已经收齐？

> **一句话结论**：通知针对流的可推进状态，TCP 不知道应用帧边界，应用必须保留每连接解码状态。

**按过程展开**：四字节长度头可能只到两个字节；一个 read 也可能返回多个完整帧和下一帧的一部分。要累积头、验证长度、累积正文，再按帧投递。还需限制最大帧、累计缓冲和半帧超时，避免合法连接数量下仍被缓冲占满。

**继续追问**：read 返回 0、-1 应如何区分？

**推导答案**：对 Java 非阻塞 SocketChannel，0 是本次没推进，-1 是流结束。不能把暂不可读当断开，也不能在 0 时无限原地重试。

**回到原理**：[对应章节](Reactor模型原理.md#p-10)。

<a id="q-04"></a>
## Q4：单 Reactor、单 Reactor 加业务池、多 Reactor 怎样演进？

> **一句话结论**：分别解决简化串行状态、隔离慢业务、扩展网络处理能力，但每一步都增加交接与容量管理。

**按过程展开**：单循环把网络和业务全做完，状态简单但慢回调阻塞其他连接。加业务池后，网络不等慢业务，仍可能卡在单循环读写解析。多循环把连接分片，降低单循环网络瓶颈，但连接负载不均和工作池过载仍需处理。

**继续追问**：多 Reactor 是否必然需要独立业务池？

**推导答案**：不必。业务足够短可就地执行；业务阻塞或很重时再隔离。模型分类应按实际读写和执行位置，而不是只数线程。

**回到原理**：[对应章节](Reactor模型原理.md#p-07)。

<a id="q-05"></a>
## Q5：“主从 Reactor”与“主从复制”有什么关系？

> **一句话结论**：前者是接受连接与已建立连接 I/O 的角色划分，后者是数据复制与高可用架构，属于不同层。

**按过程展开**：常见主 Reactor 接受连接并分配给子循环，子循环管理已建立连接的读写；子循环不是主循环的备份数据副本，也不是故障时自动接管其状态的复制节点。Nginx 的 master/worker 也不能按字面映射成这一结构。

**继续追问**：一条连接的每个请求能否随机分给不同 I/O 线程？

**推导答案**：不是不能设计，而是会增加读写、协议状态和顺序协调。常见连接归属模型就是为了避免多个线程竞争同一流状态。

**回到原理**：[对应章节](Reactor模型原理.md#p-06) · [中间件路径](Reactor中间件实践.md#m-03)。

<a id="q-06"></a>
## Q6：epoll 为什么常比 select 更适合大量连接？能说一切 O(1) 吗？

> **一句话结论**：epoll 维护关注集合并返回就绪事件，减少部分反复扫描与集合传递，但所有成本 O(1) 的说法不成立。

**按过程展开**：连接注册修改、事件唤醒、就绪结果和应用处理都有成本；当活跃连接很多时，仍有大量事件和字节要处理。select 的传统 fd_set 还有表示限制，但不能把某个平台的常见数字当跨平台契约。

**继续追问**：epoll 是否把 socket 数据直接复制到用户 Buffer？

**推导答案**：就绪机制本身不等于数据传输或零拷贝；应用通常还需调用 read/recv。sendfile 等属于其他数据路径优化。

**回到原理**：[对应章节](Reactor模型原理.md#p-08)。

<a id="q-07"></a>
## Q7：ET 下只读一部分就回到 epoll_wait，会发生什么？

> **一句话结论**：若依赖旧未读数据再次产生通知，可能停住；常见做法是读到 EAGAIN，或显式安排可靠的后续推进。

**按过程展开**：内核有 8KB，只读 1KB 后仍有旧数据。LT 可以持续报告就绪，ET 下不能依赖再次通知这部分旧状态。为防单个连接独占循环，可以使用处理预算，但预算耗尽后需要把连接保留为可继续运行并主动调度，不能盲等新边沿。

**继续追问**：ET 是否一定比 LT 快，EPOLLONESHOT 是否就是 ET？

**推导答案**：都不是。性能要测量；ONESHOT 需要重新武装，是独立选项。正确性与公平性要同时考虑。

**回到原理**：[对应章节](Reactor模型原理.md#p-09)。

<a id="q-08"></a>
## Q8：Reactor 与 Proactor 的核心区别是什么？

> **一句话结论**：一个接收就绪通知后主动推进 I/O，一个提交操作后接收该操作的完成结果。

**按过程展开**：Reactor 中收到可读，再调用 read；Proactor 中先提交读取与缓冲，之后收到该次操作的结果。完成型接口仍可能短读或失败，也仍需应用协议组帧。回调内部可以阻塞，因此完成通知不自动保证整个系统非阻塞。

**继续追问**：Java 有 CompletionHandler 就能说明底层一定是原生完成型 I/O 吗？

**推导答案**：不能。高层接口可能由不同提供者或运行时模拟实现，应区分 API 契约与操作系统后端。

**回到原理**：[对应章节](Reactor模型原理.md#p-09) · [中间件路径](Reactor中间件实践.md#m-09)。

<a id="q-09"></a>
## Q9：为什么总是关注 OP_WRITE 可能导致 CPU 空转？

> **一句话结论**：多数连接在多数时间都有发送空间，持续关注可写会反复通知，即使应用没有东西要发。

**按过程展开**：有响应时先在预算内尝试写；写不完保存当前位置，并在需要时等待可写；待发送队列清空后取消不必要的写关注。不能为了写完一个大包在事件循环原地忙等，也不能把每次返回 0 当异常直接重连。

**继续追问**：write 返回所有字节已提交，是否代表对端业务完成？

**推导答案**：只说明相应字节被本地调用接受或推进到对应层；对端接收、应用读取和业务提交都需要不同证据。

**回到原理**：[对应章节](Reactor模型原理.md#p-11)。

<a id="q-10"></a>
## Q10：使用线程池卸载业务后，为什么还会拖住 Reactor？

> **一句话结论**：任务提交、拒绝策略或回调仍可能阻塞，而且无界排队会把等待变成内存压力。

**按过程展开**：业务池满时若采用 CallerRunsPolicy，提交任务的 I/O 线程可能直接执行阻塞业务；若提交接口同步等容量，同样卡住循环。即使提交很快，无界队列也会积压，导致超时后仍执行。应定义有界容量、截止时间、拒绝与暂停读取。

**继续追问**：把队列从一千改成十万，是否就是增加吞吐？

**推导答案**：主要增加排队能力，不能增加瓶颈服务率；可能扩大内存与尾延迟。要先定位真实处理能力与允许等待预算。

**回到原理**：[对应章节](Reactor模型原理.md#p-05)。

<a id="q-11"></a>
## Q11：跨线程返回结果，为何常送回连接所属循环？

> **一句话结论**：把连接的写队列、关注事件与关闭状态集中在一个所有者中，减少并发修改与竞态。

**按过程展开**：业务线程产出安全发布的响应后投递任务并按循环协议唤醒；循环检查连接是否仍有效、请求是否过期，然后按协议排序并写入。投递失败时谁释放缓冲也要明确。仅仅使用一个并发队列，并不能自动解决唤醒丢失和连接关闭竞争。

**继续追问**：连接已经关闭，业务又完成怎么办？

**推导答案**：按关闭与取消语义丢弃或记录结果并释放资源，不能用复用的 FD 投递旧结果。操作是否已提交、是否可以重试需要业务幂等定义。

**回到原理**：[对应章节](Reactor模型原理.md#p-12)。

<a id="q-12"></a>
## Q12：TCP 保证有序，为什么并发业务结果还会乱序？

> **一句话结论**：TCP 保证发送的字节按序交付，不会替应用恢复原请求执行顺序。

**按过程展开**：请求 A 先到、B 后到，被池中两个任务并行执行，B 先完成且先写入 socket，那么 TCP 就正确地先交付 B 的响应。解决方式取决于协议：限制同连接在途任务、按序号重排，或允许带请求 ID 的乱序响应。

**继续追问**：按序号缓存是否没有代价？

**推导答案**：会增加缓冲与等待，慢的 A 可能让后面已完成的结果滞留；也要限制重排窗口并处理超时。

**回到原理**：[对应章节](Reactor模型原理.md#p-12) · [中间件路径](Reactor中间件实践.md#m-01)。

<a id="q-13"></a>
## Q13：背压为什么不能只设置一个发送缓冲上限？

> **一句话结论**：发送队列只是最后一段，已经读取和执行中的工作还会继续产生响应。

**按过程展开**：应同时限制入站累计字节、单帧大小、业务队列、在途数、结果队列与出站字节。高水位时抑制上游，低水位再恢复，避免抖动。客户端慢读时若只增加内存，服务端可能把所有业务结果一直存着直到耗尽资源。

**继续追问**：暂停读取能撤销已经提交的请求吗？

**推导答案**：不能。还要预算在途响应，必要时拒绝新工作或关闭超限连接，不能把暂停读当作完整流量控制。

**回到原理**：[对应章节](Reactor模型原理.md#p-11) · [中间件路径](Reactor中间件实践.md#m-08)。

<a id="q-14"></a>
## Q14：Netty 的 worker 为什么不是天然的业务线程池？

> **一句话结论**：worker EventLoop 主要管理连接 I/O，handler 没有额外执行器时通常就在它上面运行。

**按过程展开**：因此 handler 里直接调用阻塞 JDBC，可能让该循环管理的多条连接一起等待。可以按 handler 配置执行器、显式卸载或使用异步依赖；同时处理 ByteBuf 生命周期、超时和队列。不要把每个 handler 都卸载到不同池，否则交接本身也会成为成本。

**继续追问**：boss 线程加到很多，为什么不一定提升稳定连接上的吞吐？

**推导答案**：boss 主要处理新连接；已有连接上的网络、业务与发送瓶颈不在接受阶段。

**回到原理**：[对应章节](Reactor模型原理.md#p-06) · [中间件路径](Reactor中间件实践.md#m-01)。

<a id="q-15"></a>
## Q15：Redis 多线程 I/O 为什么不代表命令执行并行？

> **一句话结论**：网络读取、解析、写出与键空间操作是可分离阶段，Redis 普通命令的核心执行仍主要由主线程串行处理。

**按过程展开**：6/7 的批量协作路径与 8.0 新 I/O 线程事件循环实现不同，不能一图通吃。增加 I/O 线程可能减少网络侧负载，却不能直接缩短慢脚本占用主线程的时间。后台任务和模块又应单独辨别。

**继续追问**：Redis 主线程被慢命令占满，增加 I/O 线程是否解决？

**推导答案**：不能直接解决。先优化命令、拆分工作或分片，并区分网络、核心执行与持久化干扰。

**回到原理**：[对应章节](Reactor模型原理.md#p-04) · [中间件路径](Reactor中间件实践.md#m-02)。

<a id="q-16"></a>
## Q16：Nginx 的 master 是否相当于 Netty boss？

> **一句话结论**：不能直接等同，Nginx master 主要做进程管理，worker 才实际处理连接与网络事件。

**按过程展开**：多个 worker 如何接受连接受监听方式、平台与配置影响；worker 各自事件循环处理客户端和上游状态。一个代理请求可能同时占客户端与上游连接，慢下游还会引出缓冲和上游控制。

**继续追问**：Nginx 为什么也可能被磁盘或模块拖慢？

**推导答案**：网络事件驱动不等于所有文件操作和模块调用非阻塞，需看具体文件路径、线程池卸载和模块行为。

**回到原理**：[对应章节](Reactor模型原理.md#p-06) · [中间件路径](Reactor中间件实践.md#m-03)。

<a id="q-17"></a>
## Q17：Kafka 的 num.network.threads 和 num.io.threads 区别？

> **一句话结论**：前者涉及网络 Processor，后者关联请求处理池，不能把两个都当成 socket 事件循环。

**按过程展开**：Acceptor 分配连接，Processor 收取完整请求，RequestChannel 连接请求处理池，响应再回到来源 Processor。请求若等待复制或条件满足，可以走延迟完成路径；这与网络就绪循环是不同层。

**继续追问**：请求队列时间高，但网络线程很空闲，先加哪种线程？

**推导答案**：先查请求处理、存储、复制和负载；未定位前不应简单加任何池。分阶段时间比“总耗时很高”更有用。

**回到原理**：[对应章节](Reactor模型原理.md#p-13) · [中间件路径](Reactor中间件实践.md#m-04)。

<a id="q-18"></a>
## Q18：ZooKeeper 的 socket worker 与请求处理链有什么区别？

> **一句话结论**：前者处理网络层读写，后者处理请求语义、事务与一致性，线程名中的 worker 不能替代职责分析。

**按过程展开**：NIO 工厂有 accept、selector、可配置 socket worker；不用 socket worker 时 selector 可直接做 I/O。完整请求继续进入 ZooKeeperServer 的角色相关链。Netty 工厂又是另一条网络路径。

**继续追问**：写请求等 quorum 确认，增加 selector 是否有用？

**推导答案**：不直接解决业务条件等待；先看网络是否真的成为瓶颈，再定位日志、复制和请求处理链。

**回到原理**：[对应章节](Reactor模型原理.md#p-07) · [中间件路径](Reactor中间件实践.md#m-06)。

<a id="q-19"></a>
## Q19：Tomcat NIO 是否意味着 Servlet 不会阻塞？

> **一句话结论**：不意味着，NIO Connector 可以非阻塞管理连接等待，而同步 Servlet 仍可占住执行器线程。

**按过程展开**：Acceptor 接连接，Poller 检测就绪，执行器推进协议与应用。空闲 keep-alive 的等待不需要一条请求线程一直守着，但正在执行 SQL 的 Servlet 可以阻塞。异步请求也可能只是把阻塞移到另一个池。

**继续追问**：maxConnections、acceptCount、maxThreads 都是同一上限吗？

**推导答案**：不是，分别约束不同阶段；使用共享 Executor 时还要核对配置生效范围。不能只修改一个数字解释所有排队。

**回到原理**：[对应章节](Reactor模型原理.md#p-05) · [中间件路径](Reactor中间件实践.md#m-07)。

<a id="q-20"></a>
## Q20：WebFlux 返回 Mono 就能保证阻塞调用不占 I/O 线程吗？

> **一句话结论**：不能，必须区分调用时机与调度位置，响应式类型本身不改变普通函数的执行方式。

**按过程展开**：Mono.just(blockingCall()) 会先调用再包装；fromCallable 延迟调用，但还需通过适当调度器隔离阻塞源。即使放到 boundedElastic，也只是有界地迁移等待，还要控制下游连接与在途数。真正非阻塞依赖也仍有容量上限。

**继续追问**：为什么响应式 request(n) 不等于内存绝对有界？

**推导答案**：中间算子预取、调度队列、编码缓冲与出站队列是多层结构，需要端到端一起检查。

**回到原理**：[对应章节](Reactor模型原理.md#p-15) · [中间件路径](Reactor中间件实践.md#m-08)。

<a id="q-21"></a>
## Q21：虚拟线程是否会取代 Reactor？

> **一句话结论**：二者关注层次和控制方式不同，应按等待模式、协议需求与生态选择，也可能在不同层组合。

**按过程展开**：虚拟线程让顺序代码以较低平台线程成本表达大量等待，仍需限制 CPU、数据库连接和在途内存；Reactor 显式管理连接事件和状态，适合高密度网络框架，但增加状态机责任。运行时底层也可能用事件机制支撑高层等待。

**继续追问**：把阻塞服务换成虚拟线程是否就不用限流？

**推导答案**：仍需限流。等待任务更便宜，不代表下游连接、内存、CPU 或外部服务容量无限。

**回到原理**：[对应章节](Reactor模型原理.md#p-15)。

<a id="q-22"></a>
## Q22：给你一次尾延迟故障，怎样画出可验证的定位路线？

> **一句话结论**：按接受、网络循环、解析、业务排队、业务等待、结果排队和发送逐段找证据。

**按过程展开**：例如总体 CPU 不高却有心跳超时，先看单个循环线程栈、实际回调耗时与调度延迟；有无阻塞查询、锁等待或热连接。若发送字节持续积压，再查慢客户端与水位。分离队列等待、CPU 执行和外部等待，才能判断该加哪个资源。

**继续追问**：怎样证明调线程数真的有效，而不是把队列换了位置？

**推导答案**：固定连接活跃比例、请求大小与下游负载，比较吞吐、分阶段耗时、尾延迟、在途内存和拒绝率，不只看一个总吞吐数字。

**回到原理**：[对应章节](Reactor模型原理.md#p-14) · [中间件路径](Reactor中间件实践.md#m-10)。

## 综合演练：设计一个有界的查询网关

约束：2 万条长连接，平均每秒 5000 请求，每条请求调用一个平均 30ms 的外部服务，响应平均 16KiB，部分客户端停止读取。这些数字是教学输入，不是生产参数建议。

1. **先算等待规模**：稳定条件下，外部等待的平均在途数量约为 5000 × 0.03 = 150；这不包含排队和尾延迟，容量不能只按平均值设置。
2. **明确网络所有者**：少量循环分片管理连接，连接内状态与写队列由所属循环修改。
3. **明确下游调用路径**：阻塞客户端用有界池并设总在途限额；真正异步客户端也要限制并发与超时。
4. **约束所有排队点**：单帧、累计接收、任务数、响应重排、出站字节、全局预算分开限制。
5. **定义慢客户端策略**：高水位减速或暂停上游，超时或超限时按协议关闭；不能持续接收无限业务。
6. **定义顺序与取消**：请求 ID 是否支持乱序？结果迟到后谁丢弃并释放？业务已提交时超时重试如何幂等？
7. **验证退化路径**：逐步提高请求量、制造慢下游与慢读，观察拒绝、内存与尾延迟是否受控。

判断标准不是画出三个线程池，而是解释每一类资源为何有界、顺序为何正确、超时后状态如何收敛。
