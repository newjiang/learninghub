<a id="q-01"></a>
### Q1：已经加密，为什么还会被冒充？

> **一句话回答**：因为加密也可能用的是攻击者的公钥，先要确认钥匙属于谁。

**把过程讲清楚**：浏览器索要网站公钥，攻击者换成自己的；浏览器若直接接受，之后的加密只保护了到攻击者的连接。攻击者无需先破解算法。

**继续追问**：如果提前手工记住每个网站公钥呢？

**推导答案**：少量固定服务可行，但网站多且钥匙会换，PKI 用可验证担保减少逐对交换成本。

**回到故事中的这一步**：[原理对应章节](PKI原理.md#p-01)。

<a id="q-02"></a>
### Q2：证书到底是什么，谁用谁的钥匙签？

> **一句话回答**：它是对名称、公钥、期限和用途等声明的签名，签名者用 CA 自己的私钥。

**把过程讲清楚**：CA 为网站公钥背书，浏览器用 CA 公钥检查证书；网站另有自己的私钥，留待握手证明持有。两对钥匙不同，证书不应带网站私钥。

**继续追问**：网站证书公开后安全吗？

**推导答案**：证书本来可公开。安全依赖私钥和验证协议，不能靠把证书文件藏起来。

**回到故事中的这一步**：[原理对应章节](PKI原理.md#p-02)。

<a id="q-03"></a>
### Q3：网站怎样拿到证书，为什么还要验证域名？

> **一句话回答**：先生成自己的钥匙，再申请；机构必须审核名称控制，不能只信申请者自填。

**把过程讲清楚**：请求签名能证明相应密钥参与申请，却不能证明域名归申请者控制。机构可要求网页或域名记录挑战，再按策略签发合规声明。

**继续追问**：攻击者也能签自己的申请，为什么不能申请商店名称？

**推导答案**：恰恰因为还要通过商店名称的控制验证；申请持钥与域名控制是两个问题。

**回到故事中的这一步**：[原理对应章节](PKI原理.md#p-06)。

<a id="q-04"></a>
### Q4：根证书为什么可信，为什么信任不无限往上找？

> **一句话回答**：浏览器本地事先接受的信任配置提供起点，不是根自签名自己证明可靠。

**把过程讲清楚**：攻击者也能生成自签根。只有按本地策略接受的起点才提供相应授权，随后再验证中间与网站的担保链。

**继续追问**：服务端把自己的根一起发送就够了吗？

**推导答案**：不够，对方提供的材料不能自己修改客户端信任。否则攻击者发送假根就能绕过全部检查。

**回到故事中的这一步**：[原理对应章节](PKI原理.md#p-03)。

<a id="q-05"></a>
### Q5：浏览器验证证书的完整过程怎样讲？

> **一句话回答**：先找可信担保路径，再检查各级签名与权限、时间用途、目标名，最后验证本次持钥证明。

**把过程讲清楚**：只有签名正确还不够：普通网站不能任意替别人签证书，过期声明不应继续按原条件使用，别人的合法名字也不是目标服务。

**继续追问**：为什么普通网站有私钥，却不能当 CA？

**推导答案**：签名能力不等于签发授权，链验证还要检查它是否被允许签下级及范围。

**回到故事中的这一步**：[原理对应章节](PKI原理.md#p-04)。

<a id="q-06"></a>
### Q6：攻击者拿自己的合法证书，为什么不能冒充商店？

> **一句话回答**：它证明的是自己的名称，浏览器要对照原本想访问的商店名称。

**把过程讲清楚**：可信路径只证明声明有合格来源。名称列表若不包含 shop.example.test，浏览器应拒绝，即使证书签名和时间都对。

**继续追问**：两个网站在同一台服务器上呢？

**推导答案**：相同 IP 不等于相同身份，许多互不相关网站可共享服务器。SNI 帮服务器选证书，客户端仍要核对名称。

**回到故事中的这一步**：[原理对应章节](PKI原理.md#p-05)。

<a id="q-07"></a>
### Q7：证书能复制，为什么不能直接拿来冒用？

> **一句话回答**：还需要用对应网站私钥为这次握手生成有效证明。

**把过程讲清楚**：浏览器已经相信证书中的公钥，再验证本次握手签名。签名绑定协议规定的本次内容，旧签名不能直接用于任意新连接。

**继续追问**：如果连私钥也被偷了？

**推导答案**：单次握手就可能无法分清，需要换钥、吊销和状态执行，不能指望证书文件自己识别窃贼。

**回到故事中的这一步**：[原理对应章节](PKI原理.md#p-10)。

<a id="q-08"></a>
### Q8：证书、握手签名、密钥协商、密码套件如何连接？

> **一句话回答**：证书提供可信公钥，握手签名认证持钥者，临时协商建立秘密，套件指定相应记录保护等组合。

**把过程讲清楚**：可以是 CA 用 ECDSA 签网站证书，网站公钥是 RSA，握手用 RSA-PSS 认证，X25519 建立秘密，再用 AES-GCM 保护数据。每个算法站在不同岗位，组合仍须协议允许。

**继续追问**：TLS_AES_128_GCM_SHA256 说明证书必须用 RSA 吗？

**推导答案**：不说明。TLS 1.3 套件没有编码证书和具体协商组，需分别查看协商与身份信息。

**回到故事中的这一步**：[原理对应章节](PKI原理.md#p-13)。

<a id="q-09"></a>
### Q9：为什么不能简单说证书公钥加密所有网页？

> **一句话回答**：现代常见 TLS 1.3 路径分离认证与临时协商，业务记录用派生的对称密钥保护。

**把过程讲清楚**：网站签名把本次协商与可信身份绑定；双方派生不同方向与阶段的密钥，Finished 再认证握手记录。不是把证书公钥当每条 HTTP 数据的加密钥。

**继续追问**：这与历史 RSA 密钥交换有何不同？

**推导答案**：历史模式可用服务器 RSA 公钥保护密钥建立材料；不能拿那套流程解释 TLS 1.3 的临时协商。

**回到故事中的这一步**：[原理对应章节](PKI原理.md#p-13)。

<a id="q-10"></a>
### Q10：为什么需要根和中间，链越长越安全吗？

> **一句话回答**：分层是为减少根暴露和限制委派，不是靠层数增加安全。

**把过程讲清楚**：根受控授权中间，中间在线签发；按用途和组织隔离可缩小事故范围，但每多一层都有验证、传输和运维成本。

**继续追问**：中间机构名字叫内部就自然受限吗？

**推导答案**：不会，签发权限、证书约束、客户端策略与实际操作都要执行边界。

**回到故事中的这一步**：[原理对应章节](PKI原理.md#p-14)。

<a id="q-11"></a>
### Q11：私钥泄漏后，证书没过期怎么办？

> **一句话回答**：换受影响的钥和凭据，并发布提前吊销状态，由客户端按策略执行。

**把过程讲清楚**：删除本地文件不能删除攻击者副本。状态有发布、缓存和网络时延，明确吊销与查询断网是不同结果，已有会话也需单独处理。

**继续追问**：短期证书可以完全代替泄漏响应吗？

**推导答案**：不能，剩余有效窗口仍有风险，自动续签和旧连接也要管理。

**回到故事中的这一步**：[原理对应章节](PKI原理.md#p-07)。

<a id="q-12"></a>
### Q12：双向证书认证成功，为什么还不能直接允许结算？

> **一句话回答**：证明身份不等于授予全部业务权限。

**把过程讲清楚**：服务端检查客户端证书和持钥证明，映射到服务账号，再判断此账号能否对这笔订单执行结算。同根的仓储服务不自然拥有结算权。

**继续追问**：内部自建 CA 是否就不用管理信任了？

**推导答案**：仍要可信分发根、审核申请、保护私钥、轮换吊销和审计，只是信任范围可由组织控制。

**回到故事中的这一步**：[原理对应章节](PKI原理.md#p-09)。

<a id="q-13"></a>
### Q13：怎样从故障看出 PKI 的各层职责？

> **一句话回答**：根据失败发生在链、名称、时间、持钥还是授权阶段修对应问题。

**把过程讲清楚**：浏览器有中间缓存而程序没有，可能解释链差异；错名称需修目标或身份范围；钥不配对需修持钥配置；都不应统一关闭验证。

**继续追问**：CA 已签错该由哪一层发现？

**推导答案**：透明日志、所有者监测与机构审计提高发现能力，发现后仍要吊销和治理；日志记录本身不证明签发无误。

**回到故事中的这一步**：[原理对应章节](PKI原理.md#p-12)。

## 练习：用六句话连起来

1. 只拿公钥会被替换，所以需要可信身份声明。
2. 网站自己保管私钥，审核机构验证名称控制后为其公钥签证书。
3. 浏览器从本地信任起点验证担保链、权限、时间和目标名称。
4. 网站还要为本次握手签名，证明当前对端真有网站私钥。
5. 双方按协议协商并派生会话密钥，用相应密码套件保护业务记录。
6. 后续还需续证、换钥、吊销、异常签发监测和信任更新。
