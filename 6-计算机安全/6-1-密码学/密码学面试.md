### Q1：加密、摘要、MAC 和签名怎样区分？

> **一句话结论**：分别面向保密、无密钥指纹、共享密钥认证和公开可验来源证据。

**机制展开**：先问需要什么能力。保密要加密，分对称与公钥加密；内容指纹用哈希，没有解密接口；共享密钥双方验真用 MAC；需要不持秘密的第三方也能验证来源，用签名。密钥协商和派生则负责建立、加工秘密，是另外两类职责。

如果文件和摘要同时被替换，无密钥哈希不能证明来源。MAC 接收者也持有同一秘密，因而能生成相同类型的有效标签，不能靠它区分双方责任。签名验证者只拿公钥，一般不能据此生成新签名，但签名本身不隐藏消息，公钥的身份归属也须另行可信确认。

**具体推演**：攻击者替换文件与旁边 SHA-256 文本，摘要仍一致却不能证明发布者。

**⚖️ 方案对比与代价**：按威胁模型选原语，减少秘密分发或获得公开验证都伴随不同信任和性能成本。

**🔎 追问演练**：签名能否自动证明操作已授权？

**推演要点**：不能，持钥身份和业务权限必须另有策略。

**原理展开**：[分类与能力对照](密码学原理.md#p-00)。

<a id="q-02"></a>
### Q2：DH 的相同结果为何不等于安全身份？

> **一句话结论**：代数一致只建立秘密，未认证交换仍可被中间人分成两条会话。

**机制展开**：公开份额与秘密指数生成相同共享值，攻击者替换份额后可各自协商并转发。

**具体推演**：玩具 p=23 算例两边都得到 2，只验证公式；主动攻击仍需额外认证机制阻止。

**⚖️ 方案对比与代价**：标准群和成熟实现减少参数风险，签名与握手绑定增加认证成本但不可省。

**🔎 追问演练**：用大数字就一定安全？

**推演要点**：还看群阶、结构、参数、输入验证与已知攻击，不由十进制长度决定。

**原理展开**：[密码学对应章节](密码学原理.md#p-02)。

<a id="q-03"></a>
### Q3：AES 安全为何还会泄漏数据？

> **一句话结论**：原语安全不保证模式、nonce、认证与实现正确。

**机制展开**：ECB 暴露相同块，CTR 复用密钥流泄漏异或关系，CBC 无认证可遭主动修改。

**具体推演**：同密钥流下两个密文异或等于明文异或，不需要先求出密钥。

**⚖️ 方案对比与代价**：AEAD 统一认证与保密更易正确组合，仍需遵守模式与使用次数限制。

**🔎 追问演练**：随机 nonce 就永远不会碰撞吗？

**推演要点**：不是，需预算随机空间、消息量和多实例策略，计数方案也需防回滚。

**原理展开**：[密码学对应章节](密码学原理.md#p-03)。

<a id="q-04"></a>
### Q4：GCM nonce 重复为什么严重？

> **一句话结论**：同密钥下重复会破坏保密与认证保证，可能帮助伪造。

**机制展开**：重复计数输入导致密钥流和认证关系异常，不能仅当随机性稍差处理。

**具体推演**：虚拟机快照恢复使计数器回退，多个实例再发出相同 nonce，算法库也救不了错误输入。

**⚖️ 方案对比与代价**：集中计数、实例分区或受控随机各有状态和碰撞成本，密钥轮换需保持标识一致。

**🔎 追问演练**：标签验证失败前能否输出部分明文？

**推演要点**：不应交给业务，未认证内容必须隔离，验证失败不产生副作用。

**原理展开**：[密码学对应章节](密码学原理.md#p-04)。

<a id="q-05"></a>
### Q5：AEAD 认证了为什么还要防重放？

> **一句话结论**：合法密文再次发送仍可能合法，认证不隐式记录历史。

**机制展开**：接收端需序号窗口、请求 ID 或其他状态，AAD 可绑定上下文但不是自动去重数据库。

**具体推演**：同一扣款密文原封重发，标签仍有效，业务需判断是否已处理。

**⚖️ 方案对比与代价**：有状态防重放增加存储与集群协调，幂等降低副作用但不替代身份认证。

**🔎 追问演练**：只加时间戳可以吗？

**推演要点**：窗口内仍可重放，还要考虑时钟偏差和重复检测。

**原理展开**：[密码学对应章节](密码学原理.md#p-04)。

<a id="q-06"></a>
### Q6：密码为什么不用一次 SHA-256 加盐？

> **一句话结论**：口令熵低，需刻意增加每次离线猜测成本，盐不阻止单条逐个猜。

**机制展开**：时间和内存硬化方案让猜测更贵，盐隔离预计算，独立秘密 pepper 还涉及密钥管理。

**具体推演**：同一弱口令即使每用户盐不同，攻击者仍可分别尝试常见字典。

**⚖️ 方案对比与代价**：参数过低抗猜弱，过高拖垮登录容量；保留参数版本与升级能力。

**🔎 追问演练**：HKDF 能直接代替口令哈希吗？

**推演要点**：输入假设不同，通用秘密派生不自动提供相同离线抗猜成本。

**原理展开**：[密码学对应章节](密码学原理.md#p-05)。

<a id="q-07"></a>
### Q7：临时 DH 怎样提供前向安全？

> **一句话结论**：正确临时协商与秘密销毁使后来长期签名钥泄漏不直接恢复此前会话秘密。

**机制展开**：签名负责认证份额与上下文，临时秘密负责共享值，KDF 再分用途生成密钥。

**具体推演**：攻击者只记录握手、之后拿到证书签名私钥，不应据此直接算出已销毁临时秘密。

**⚖️ 方案对比与代价**：保护历史记录但不抗当时端点失陷；PSK 恢复还需按具体模式分析。

**🔎 追问演练**：同一共享值直接用于双向全部用途可以吗？

**推演要点**：应按方向、阶段和用途分域派生，避免跨协议复用。

**原理展开**：[密码学对应章节](密码学原理.md#p-06)。

<a id="q-08"></a>
### Q8：签名是不是私钥加密？

> **一句话结论**：不应这样概括，签名是有独立编码、验证规则和安全目标的方案。

**机制展开**：RSA-PSS 与 OAEP 各有不同接口，ECDSA/EdDSA 更不是通用私钥加密的反向操作。

**具体推演**：验签者验证规范化字节与参数，不是在任意签名中解出原始大文件。

**⚖️ 方案对比与代价**：公开验证有利第三方证据，但密钥控制、时间和审计仍影响责任判断。

**🔎 追问演练**：相同 JSON 对象为何验签失败？

**推演要点**：签名处理字节，顺序、空白、数字和 Unicode 编码需协议规范化。

**原理展开**：[密码学对应章节](密码学原理.md#p-07)。

<a id="q-09"></a>
### Q9：为什么 KMS 信封加密还要保护应用权限？

> **一句话结论**：模块保护密钥不导出不阻止已获授权的失陷应用请求解密。

**机制展开**：数据密钥保护内容，上层密钥包装数据密钥，调用权限、上下文和审计仍是边界。

**具体推演**：攻击者控制一个合法服务身份，可滥用其解密 API 而无需偷出根密钥。

**⚖️ 方案对比与代价**：集中密钥便于审计轮换却有可用性与权限集中风险，应最小授权并隔离用途。

**🔎 追问演练**：重包数据密钥能修复数据密钥已泄漏吗？

**推演要点**：不能自动修复，旧内容可能需要新数据钥重新保护并分析历史暴露。

**原理展开**：[密码学对应章节](密码学原理.md#p-08)。

<a id="q-10"></a>
### Q10：后量子 KEM 和签名能互换吗？

> **一句话结论**：不能，KEM 建立共享秘密，签名提供来源验证，角色不同。

**机制展开**：ML-KEM 与 ML-DSA 分别标准化不同功能，迁移还涉及证书、协议及握手大小。

**具体推演**：只把协商换成后量子方案，不自动把旧签名链变成抗量子身份体系。

**⚖️ 方案对比与代价**：混合策略与敏捷性降低迁移风险却增加兼容成本，不能自行拼接后宣称完整安全。

**🔎 追问演练**：标准发布是否等于所有 TLS 栈可用？

**推演要点**：不等于，还需协议集成、实现支持、策略和真实互操作验证。

**原理展开**：[密码学对应章节](密码学原理.md#p-10)。

<a id="q-11"></a>
### Q11：TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256 中 RSA 和 SHA256 分别干什么？

> **一句话结论**：RSA 对应认证签名角色，SHA256 在该 AEAD 套件定义中关联 PRF 哈希，不是额外记录 HMAC。

**机制展开**：ECDHE 建立秘密，RSA 认证，AES-GCM 保护记录，具体组与签名参数还要继续看扩展和证书。

**具体推演**：与 TLS_RSA_WITH... 的历史路径比较，RSA 位置看似相近却对应不同密钥建立语义。

**⚖️ 方案对比与代价**：名称浓缩组合但不能跨版本套固定解析口诀，历史套件也不等于推荐配置。

**🔎 追问演练**：AES_128 是证书公钥只有 128 位吗？

**推演要点**：不是，它说明 AES 对称密钥位数，公钥参数、标签长度和哈希输出是其他维度。

**原理展开**：[TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256 中 RSA 和 SHA256 分别干什么？](密码学原理.md#p-12)。

<a id="q-12"></a>
### Q12：TLS 1.3 套件名没有 RSA，为何仍能用 RSA 证书？

> **一句话结论**：TLS 1.3 将套件与认证、协商组分开选择，套件主要确定 AEAD 与相关哈希。

**机制展开**：服务端仍可使用相应 RSA 签名能力的证书完成证书认证，临时协商与记录保护独立。

**具体推演**：同一 TLS_AES_128_GCM_SHA256 可在满足其他约束时与不同签名和协商组合一起出现。

**⚖️ 方案对比与代价**：分离减少套件组合膨胀，却要求诊断同时记录版本、套件、组与签名，不能只截一个名称。

**🔎 追问演练**：套件相同是否说明两次握手安全条件完全相同？

**推演要点**：不说明，身份验证、恢复模式、临时组、密钥生命周期和端点策略可能不同。

**原理展开**：[TLS 1.3 套件名没有 RSA，为何仍能用 RSA 证书？](密码学原理.md#p-12)。

<a id="q-13"></a>
### Q13：有共同密码套件为什么仍握手失败？

> **一句话结论**：套件仅覆盖部分算法选择，版本、组、签名、证书和身份约束仍需同时成立。

**机制展开**：TLS 1.3 将这些维度分离，支持列表重叠也不证明所需份额、私钥能力或信任条件齐全。

**具体推演**：双方都允许 AES-GCM，却只有一方接受当前证书可提供的签名方案，认证仍无法完成。

**⚖️ 方案对比与代价**：诊断更复杂但角色更清楚，应记录完整协商元数据而非只改套件字符串。

**🔎 追问演练**：HelloRetryRequest 是让客户端重验一次证书吗？

**推演要点**：不是，它按协议请求适当的新 ClientHello 等信息，可能与缺少合适 key_share 有关。

**原理展开**：[有共同密码套件为什么仍握手失败？](密码学原理.md#p-13)。

<a id="q-14"></a>
### Q14：AES-256 套件一定比 AES-128 更适合所有服务吗？

> **一句话结论**：不能只按位数决定完整系统方案，还要看安全需求、平台性能和协议边界。

**机制展开**：套件不控制根信任、身份匹配或 nonce 管理，其他环节错误无法由更长密钥修复。

**具体推演**：证书名字不匹配时换 AES-256 仍应失败，重复 nonce 的错误也不会自然消失。

**⚖️ 方案对比与代价**：按威胁和兼容性选择允许集合，保留版本化迁移与观测，避免无目的启用全部旧项。

**🔎 追问演练**：关闭早期数据是否必须关闭恢复？

**推演要点**：不必，0-RTT 与恢复不是同一开关语义，应按具体协议栈分别配置和验证。

**原理展开**：[AES-256 套件一定比 AES-128 更适合所有服务吗？](密码学原理.md#p-13)。

<a id="q-15"></a>
### Q15：“单向、可逆、对称、非对称”应该怎样分类？

> **一句话结论**：可逆与单向描述恢复能力，对称与非对称描述密钥关系，它们不能直接当成同一层分类。

**按过程讲清楚**：先用业务区分：收货地址要恢复，用可逆加密；登录口令只验证，用专用口令验证记录；软件发布要公开验证来源，用签名。然后在加密内部分对称与公钥加密，再单列哈希、MAC、签名、协商和派生。

非对称密码学范围比公钥加密大：ECDSA 是签名，X25519 是协商，都不是任意消息加解密接口。所谓“单向加密”通常在指哈希，正式表述应避免让人误以为存在解密密钥。

**继续追问**：给数据库里的手机号做 SHA-256，它是否已经保密？

**推导答案**：手机号输入空间有限，可以枚举重算；若业务要恢复原值更不满足需求。需明确可逆保护、查询能力与索引泄漏模型。

**原理展开**：[对应原理](密码学原理.md#p-00)。

<a id="q-16"></a>
### Q16：Base64、CRC、SHA-256 为什么不能互相替代？

> **一句话结论**：它们分别面向表示转换、偶发错误检测和密码学指纹，安全目标不同。

**按过程讲清楚**：Base64 有公开还原规则，知道规则即可还原。CRC 有利于检测偶发位错误，但主动攻击者可重算。SHA-256 设计上抵抗特定搜索攻击，但它也是公开函数；文件与旁边的摘要一起被替换时，比较成功不能证明发布者。

若摘要通过独立可信渠道固定，则可用于比对下载内容；若希望任何人验证发布者，通常需要可信公钥对应的数字签名。结论要带上“期望摘要从哪里得到”的条件。

**继续追问**：把 Base64 连做三次，会比一次 AES 更安全吗？

**推导答案**：多次公开编码仍能逐层还原，并没有秘密密钥或保密困难性；层数不是安全强度。

**原理展开**：[对应原理](密码学原理.md#p-00)。

<a id="q-17"></a>
### Q17：哈希不可逆，为什么数据库口令泄漏后仍会被破解？

> **一句话结论**：攻击者可以猜输入再正向计算，不需要找到哈希函数的通用逆算法。

**按过程讲清楚**：攻击者取得算法、盐、成本参数与验证值后，对词典和规则生成的候选逐个计算。盐使跨用户和预计算复用困难，却不阻止针对单条记录猜测。高成本口令派生增加每个候选的时间和内存消耗，强口令减少可预测性。

因此要同时看口令强度、派生成本、记录泄漏和在线限速。在线限速不能直接限制已经拿到记录的离线攻击；只使用快速 SHA-256 则把大量候选的成本降得很低。

**继续追问**：为什么用户忘记口令一般应重置，而不是找回原文？

**推导答案**：合适的验证记录没有解密接口。找回原文意味着系统保存了额外可恢复材料，需要审视其必要性与泄漏影响。

**原理展开**：[对应原理](密码学原理.md#p-05)。

<a id="q-18"></a>
### Q18：AES-256 的 256 是分组大小吗，AES 怎样能够解密？

> **一句话结论**：256 是密钥位数，AES 分组始终是 128 位；解密利用轮变换与密钥安排的对应逆操作。

**按过程讲清楚**：AES 在 16 字节状态上组合非线性字节替换、位置移动、列混合和子密钥异或，多轮构造依赖密钥的置换。AES-128、192、256 分别使用 10、12、14 轮。合法方有密钥可以执行对应逆运算；攻击者不能仅因为知道算法步骤就得到密钥。

但这只解释原语的结构与正确性；处理多块消息还需模式，验证主动篡改还需认证。AES-256 加上重复 GCM nonce，仍会破坏方案安全。

**继续追问**：128 位分组是否意味着只能加密 16 字节文件？

**推导答案**：原语每次处理一个分组，模式负责处理多块、尾块及所需附加信息；文件长度不是分组大小。

**原理展开**：[对应原理](密码学原理.md#p-03)。

<a id="q-19"></a>
### Q19：CBC、CTR 与 GCM 的差别，应该怎样从公式解释？

> **一句话结论**：CBC 串接前块密文，CTR 生成密钥流，GCM 在计数器加密基础上加入认证结构。

**按过程讲清楚**：CBC 加密是 Ci=E(K,Pi xor C(i-1))，因此加密有前块依赖，通常需填充；解密块密码操作可并行。CTR 是 Pi 与相应计数输入生成的密钥流异或，可并行且不需块填充，但同密钥计数输入不能重复。

CBC 与 CTR 单独均无完整消息认证保证。GCM 认证 AAD 与密文等信息，输出标签，接收者应在认证成功前隔离未验证明文；仍需保证 nonce 唯一并遵守使用预算。

**继续追问**：CBC 为什么会发生填充预言机攻击？

**推导答案**：修改前块可影响后块明文，服务端暴露填充有效性会提供反复试探的反馈；需正确的认证保护与实现处理，不能仅改提示文案。

**原理展开**：[对应原理](密码学原理.md#p-03)。

<a id="q-20"></a>
### Q20：抗碰撞、原像抗性与第二原像抗性怎样区别？

> **一句话结论**：分别是找任意一对同摘要消息、对指定摘要找输入、对指定消息找另一个同摘要输入。

**按过程讲清楚**：如果攻击者可预先设计两份合同，试图让两份摘要相同，这是碰撞模型；如果合同已固定，想找另一份替代它，是第二原像模型；如果只有一个验证值，要找任何符合值的输入，是原像模型。

对理想 n 位输出，通用碰撞搜索量级约为 2^(n/2)，通用原像搜索约为 2^n。但若输入只有一百万个候选，枚举输入只需考虑该小空间，不能拿 2^256 估算六位口令的破解成本。

**继续追问**：摘要同为 256 位，是否说明所有安全性质和使用方式完全相同？

**推导答案**：不能，输出长度只是一个维度，还看构造、已知攻击、协议对性质的依赖与输入分布。

**原理展开**：[对应原理](密码学原理.md#p-05)。

<a id="q-21"></a>
### Q21：RSA 为什么不能直接加密大文件，OAEP 和 PSS 各做什么？

> **一句话结论**：RSA-OAEP 是带编码的公钥加密方案，RSA-PSS 是签名方案；前者单次明文长度受模数和摘要长度限制。

**按过程讲清楚**：OAEP 上限是 k-2×hLen-2 字节，k 是模数字节数。2048 位模数配 SHA-256 时为 190 字节，远小于常见文件。裸 RSA 的确定性与代数结构也使“分块直接算模幂”不成为安全文件格式。

应采用标准混合加密：随机数据密钥通过认证加密保护内容，再用标准公钥方案封装或保护数据密钥。PSS 解决的是签名编码，输出供公钥验证，不是 OAEP 的反向调用。

**继续追问**：公钥是公开的，那么成功解密是否证明发送者可信？

**推导答案**：不证明。任何人都能用真实接收者公钥制作新密文，发送者认证需要另有协议证明。

**原理展开**：[对应原理](密码学原理.md#p-07)。

<a id="q-22"></a>
### Q22：X25519、Ed25519、ECDSA 和 ECC 能当同类算法互换吗？

> **一句话结论**：ECC 是家族，ECDSA 与 Ed25519 用于签名，X25519 用于协商，不能按名称相近直接互换。

**按过程讲清楚**：先标出职责：签名需要消息与私钥，输出签名；协商需要本地秘密与对端公开材料，输出共同秘密。曲线参数只是基础，具体接口和编码还有协议定义。

临时协商若未认证可被中间人替换；签名若验证了攻击者自己提供的公钥，也不能确认真实身份。证书链解决公钥与身份绑定，握手签名绑定本次交换，KDF 再派生方向与阶段分离的流量密钥。

**继续追问**：ECDSA 每次签名的秘密量与 AES-GCM nonce 都叫随机数，它们要求一样吗？

**推导答案**：不一样。前者必须按标准保持秘密并避免错误复用，后者通常可公开但同密钥必须唯一。秘密性、唯一性和不可预测性应分别判断。

**原理展开**：[对应原理](密码学原理.md#p-07)。
