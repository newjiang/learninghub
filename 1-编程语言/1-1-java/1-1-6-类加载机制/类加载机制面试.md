### Q1：加载、链接、初始化如何区分？

> **一句话结论**：加载建立运行时类型，链接验证准备解析，初始化执行静态初始化逻辑。

**机制展开**：解析允许延迟，不能把生命周期图理解成所有符号先一次性解析完。

**⚖️ 方案对比与代价**：规范时序与某版实现要区分，先判断具体观察点。

**🔎 追问演练**：拿到 Class 是否 static 块已执行？

**推演要点**：不一定，类字面量、禁止初始化的查找等都可能拿到 Class 而未初始化。

**原理展开**：[类加载机制原理对应章节](类加载机制原理.md#p-01)。

<a id="q-02"></a>
### Q2：static final 一定不会触发初始化吗？

> **一句话结论**：只有具体编译期常量使用才适用相应规则，final 本身不够。

**机制展开**：int 常量可内联，Integer 或方法返回值通常需要运行时初始化；读取继承字段看实际声明类。

**⚖️ 方案对比与代价**：常量内联降低运行期开销，却可能让旧调用方保留旧值。

**🔎 追问演练**：修改公共常量为何重启调用方仍是旧值？

**推演要点**：检查是否重新编译了使用方，旧字节码可能已嵌入旧常量。

**原理展开**：[类加载机制原理对应章节](类加载机制原理.md#p-02)。

<a id="q-03"></a>
### Q3：Class.forName 与 loadClass 有什么区别？

> **一句话结论**：默认 Class.forName 初始化，loadClass 通常只加载，显式参数还能控制前者。

**机制展开**：创建数组、读取编译期常量也不能简单等同主动初始化组件或声明类。

**⚖️ 方案对比与代价**：需要扫描元数据时避免不必要初始化，实际实例化再按需触发。

**🔎 追问演练**：new Child 和 Child.parentField 为什么输出不同？

**推演要点**：区分构造子类与访问父类声明静态字段，各自初始化范围不同。

**原理展开**：[类加载机制原理对应章节](类加载机制原理.md#p-03)。

<a id="q-04"></a>
### Q4：类初始化失败还能重试吗？

> **一句话结论**：同一运行时类一旦标记初始化错误，后续使用通常继续失败。

**机制展开**：首次常见初始化包装错误，后续可能 NoClassDefFoundError；JVM 不自动重新运行失败的 static 块。

**⚖️ 方案对比与代价**：避免在 static 初始化做不稳定远端调用，必要的可重试初始化应显式管理状态。

**🔎 追问演练**：为什么日志后来都只剩无法初始化类？

**推演要点**：保留并追溯首次触发的原始异常，后续异常可能只是错误状态的结果。

**原理展开**：[类加载机制原理对应章节](类加载机制原理.md#p-03)。

<a id="q-05"></a>
### Q5：双亲委派是什么，必须遵循吗？

> **一句话结论**：它是典型父优先策略，不是所有加载器不可修改的语言定律。

**机制展开**：通常先查已加载，再委派父，找不到才 findClass；它帮助共享基础类型。

**⚖️ 方案对比与代价**：局部优先可隔离依赖，但必须共享接口和保护平台命名空间。

**🔎 追问演练**：为什么建议覆盖 findClass 而非全重写 loadClass？

**推演要点**：可复用委派、已加载检查和协调协议，降低重复定义与并发错误。

**原理展开**：[类加载机制原理对应章节](类加载机制原理.md#p-04)。

<a id="q-06"></a>
### Q6：两个同名类为什么不能强转？

> **一句话结论**：运行时类型身份还包含定义加载器。

**机制展开**：同一二进制名由两个隔离加载器各自定义就是两个类型，接口签名中的参数类也要保持一致。

**⚖️ 方案对比与代价**：共享 API 放公共父，插件内部依赖隔离；边界对象需统一类型或显式序列化协议。

**🔎 追问演练**：父接口共享但 DTO 不共享会怎样？

**推演要点**：方法交互仍可能因签名类型不一致发生加载约束错误或强转失败。

**原理展开**：[类加载机制原理对应章节](类加载机制原理.md#p-05)。

<a id="q-07"></a>
### Q7：SPI 为什么常用 TCCL？

> **一句话结论**：上层框架需要发现应用层提供者，单靠自己的父优先可见域未必够。

**机制展开**：线程上下文加载器由调用环境提供发现路径，ServiceLoader 按相应配置找实现。

**⚖️ 方案对比与代价**：可扩展但增加生命周期责任，临时切换必须恢复。

**🔎 追问演练**：池线程持有旧插件 TCCL 有何影响？

**推演要点**：长寿命线程成为旧加载器根引用，插件即使停止也可能无法卸载。

**原理展开**：[类加载机制原理对应章节](类加载机制原理.md#p-06)。

<a id="q-08"></a>
### Q8：类加载器 close 等于卸载吗？

> **一句话结论**：不等于，资源关闭与类不可达、卸载是不同事件。

**机制展开**：类、实例、反射对象、线程上下文等都可能间接保留加载器。

**⚖️ 方案对比与代价**：新加载器重载得到新身份，需要明确停止旧任务和解除注册。

**🔎 追问演练**：把一个 Class 变量赋 null 为什么没用？

**推演要点**：检查其余引用链和线程根，单一局部引用消失不代表整个加载器对象图不可达。

**原理展开**：[类加载机制原理对应章节](类加载机制原理.md#p-07)。

<a id="q-09"></a>
### Q9：ClassNotFoundException 和 NoClassDefFoundError 一样吗？

> **一句话结论**：不是，显式查找失败与链接或使用时定义不可用属于不同情形。

**机制展开**：后者还可能由之前初始化失败造成；应结合首次原因、加载器和调用阶段分析。

**⚖️ 方案对比与代价**：直接补 jar 可能掩盖真正的版本或初始化问题。

**🔎 追问演练**：为什么 class 在 jar 里却仍失败？

**推演要点**：可能加载器不可见、依赖缺失、版本不兼容或初始化已失败，逐阶段检查。

**原理展开**：[类加载机制原理对应章节](类加载机制原理.md#p-08)。

<a id="q-10"></a>
### Q10：初始化为什么可能死锁？

> **一句话结论**：不同类的初始化与线程等待可以形成环。

**机制展开**：A 初始化等待线程 B，B 又需要使用尚未完成初始化的 A，彼此都无法推进。

**⚖️ 方案对比与代价**：静态初始化保持轻量，避免线程启动后 join、外部锁和复杂资源依赖。

**🔎 追问演练**：一个类的初始化只执行一次是否意味着没有并发风险？

**推演要点**：一次执行不排除跨类等待环，也不保护后续静态可变字段。

**原理展开**：[类加载机制原理对应章节](类加载机制原理.md#p-03)。

<a id="q-11"></a>
### Q11：解析了方法以后为什么还要动态分派？

> **一句话结论**：符号引用解析与根据实际接收者选择覆写实现承担不同责任。

**机制展开**：常量池描述声明关系，虚调用依据对象类型按规则选择实现，运行时可优化但须保持语义。

**⚖️ 方案对比与代价**：静态调用、特殊调用与虚调用要分开，不能按一个“运行期绑定”概括所有方法。

**🔎 追问演练**：变量声明为父类是否必然执行父类覆写方法？

**推演要点**：普通虚调用仍看实际接收者，重载选择与覆写分派也不是同一步。

**原理展开**：[类加载机制深入机制](类加载机制原理.md#p-09)。

<a id="q-12"></a>
### Q12：Lambda 和匿名内部类完全一样吗？

> **一句话结论**：不是，词法 this、捕获与常见字节码链接路径都不同。

**机制展开**：Lambda 常经 invokedynamic 和引导方法建立函数对象路径，链接与每次实例创建不是一回事。

**⚖️ 方案对比与代价**：业务依赖接口行为而非生成类名或对象复用，捕获可变对象仍有共享风险。

**🔎 追问演练**：effectively final 能保证捕获对象线程安全吗？

**推演要点**：只限制该局部引用重赋值，不保护对象内部状态。

**原理展开**：[类加载机制深入机制](类加载机制原理.md#p-09)。

<a id="q-13"></a>
### Q13：同一份 class 字节为什么仍能生成不兼容对象？

> **一句话结论**：定义加载器参与运行时类型身份，字节内容相同并不够。

**机制展开**：两个加载器各自定义同名类型，isInstance 与强转按身份判断而非比较源码。

**⚖️ 方案对比与代价**：共享接口要连同签名类型一起共享，或改用有版本的字节协议。

**🔎 追问演练**：为什么只统一接口 jar 仍失败？

**推演要点**：检查参数、返回值、异常与嵌套模型是否仍由两边各自定义。

**原理展开**：[类加载机制深入机制](类加载机制原理.md#p-10)。

<a id="q-14"></a>
### Q14：插件换了新加载器为什么旧内存没释放？

> **一句话结论**：新身份的建立不切断旧对象、任务和缓存的保留链。

**机制展开**：长寿命线程、回调注册、TCCL 与反射缓存仍可引用旧加载域。

**⚖️ 方案对比与代价**：需要生命周期交接而非只 new 一个加载器，卸载时机还受虚拟机控制。

**🔎 追问演练**：URLClassLoader.close 可以作为卸载完成证明吗？

**推演要点**：不行，资源关闭与旧类型不再可达不是同一事件。

**原理展开**：[类加载机制深入机制](类加载机制原理.md#p-10)。
