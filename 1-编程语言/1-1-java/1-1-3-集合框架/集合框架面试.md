### Q1：ArrayList 和 LinkedList 怎么选？

> **一句话结论**：先拆开定位与修改成本，普通列表通常从 ArrayList 开始，LinkedList 的局部修改优势必须建立在已定位节点上。

**机制展开**：数组按下标定位为 O(1)，中间插删要移动引用；链表按下标定位仍是 O(n)，且每个节点有额外引用和分配成本。ListIterator 已定位后才有局部链接修改优势。

**⚖️ 方案对比与代价**：链表避免大段搬移，但缓存局部性与内存开销通常较差；数组扩容有峰值，预估容量可减少复制。

**🔎 追问演练**：为什么链表下标遍历会慢到 O(n²)？

**推演要点**：每次 get(i) 都重新沿节点定位，累计步数是等差数列；改用迭代器消除重复定位，但不能据此宣称链表必然更快。

**原理展开**：[集合框架原理对应章节](集合框架原理.md#c-02)。

<a id="q-02"></a>
### Q2：ArrayList 为什么是摊还 O(1) 追加？

> **一句话结论**：多数追加只写一个槽位，少数扩容复制旧引用，几何增长把总复制成本摊到多次追加。

**机制展开**：现代实现按旧容量约一半的首选增量增长，并受最小需求、溢出和数组上限约束；默认构造还涉及延迟分配。复制的是引用，元素对象不会被逐个深复制。

**⚖️ 方案对比与代价**：预分配减少扩容但可能浪费内存；clear 释放元素引用而通常保留容量，频繁 trim 又会制造复制成本。

**🔎 追问演练**：扩容后修改同一个元素对象，旧持有者能看到吗？

**推演要点**：对象身份没有改变；列表结构副本与对象深副本必须分开。也不要把某次扩容公式当作 List 接口契约。

**原理展开**：[集合框架原理对应章节](集合框架原理.md#c-03)。

<a id="q-03"></a>
### Q3：为什么队列和栈常用 ArrayDeque？

> **一句话结论**：单线程双端操作可用循环数组减少节点分配，并以明确的首尾方法表达栈或队列。

**机制展开**：首尾位置环绕移动；增长需要复制，不能推断每次操作最坏恒定。ArrayDeque 禁止 null，poll 返回 null 才能表达空。

**⚖️ 方案对比与代价**：LinkedList 也支持双端，但通常节点开销更高；并发环境需要另外选择并发或阻塞结构。

**🔎 追问演练**：Stack 的方法同步是否保证先检查再 pop 安全？

**推演要点**：两次方法调用之间可发生其他线程操作，组合不变量仍需共同同步；旧类方法安全不是业务事务。

**原理展开**：[集合框架原理对应章节](集合框架原理.md#c-04)。

<a id="q-04"></a>
### Q4：equals 与 hashCode 为什么必须一起设计？

> **一句话结论**：相等对象必须同哈希，哈希相同不要求对象相等，而且键参与比较的状态在存储期间应保持稳定。

**机制展开**：先依据哈希定位桶，再用等价规则找到键；修改哈希字段可能让对象留在旧桶，查询却转向新桶。数组默认使用引用相等，不能自动得到内容键。

**⚖️ 方案对比与代价**：对象身份、值相等、排序比较是不同模型；BigDecimal 的 equals 与 compareTo 也不同，换 Set 实现可能改变去重结果。

**🔎 追问演练**：为什么遍历看得到键而 get 却找不到？

**推演要点**：遍历扫描存储结构，get 按键当前哈希定位；检查可变键，而非直接认定 Map 数据消失。

**原理展开**：[集合框架原理对应章节](集合框架原理.md#c-05)。

<a id="q-05"></a>
### Q5：HashMap 为什么用二次幂容量？

> **一句话结论**：参考实现通过位掩码分桶，并让翻倍迁移按旧容量位把原桶拆成两组。

**机制展开**：扰动让高位参与低位分布；索引为 (n-1)&hash。翻倍后只多出 oldCap 这一位，节点去原索引或原索引加 oldCap。

**⚖️ 方案对比与代价**：索引计算简单但仍依赖哈希质量；扩容涉及分配和迁移，预估映射数与构造容量不是同一数字。

**🔎 追问演练**：容量 16、负载因子 0.75 为什么通常装不到 16 项就扩？

**推演要点**：阈值依据容量乘负载因子，常规插入超过阈值触发；碰撞场景还可能因树化前置条件提前扩容。

**原理展开**：[集合框架原理对应章节](集合框架原理.md#c-06)。

<a id="q-06"></a>
### Q6：HashMap 是不是第八个元素必然树化？

> **一句话结论**：不是；阈值常量、入口的计数方式、桶原有长度和表容量共同决定行为。

**机制展开**：参考常规 put 路径：桶已有八个节点再插入第九个时尝试树化，表容量小于 64 时优先扩容。compute 等路径的计数不可简单照搬。

**⚖️ 方案对比与代价**：树桶增加节点和维护成本，小表扩容可能更便宜；普通删除退树还涉及形态判断，不能统一写成节点少于六就退化。

**🔎 追问演练**：树化后恶意碰撞查找一定 O(log n) 吗？

**推演要点**：红黑树高度对数不等于所有相同哈希且不可比较键的查找路径都严格对数，仍须讨论等价与比较条件。

**原理展开**：[集合框架原理对应章节](集合框架原理.md#c-07)。

<a id="q-07"></a>
### Q7：HashMap 在并发下为什么不能用？

> **一句话结论**：它没有提供并发更新与发布协议，现代版本即使没有旧版迁移环问题，也可能丢更新或读到不可靠状态。

**机制展开**：竞争插入可覆盖状态，扩容与读取缺少所需同步；失败快速异常只是尽力检测，不会修复数据竞争。

**⚖️ 方案对比与代价**：外部同一把锁可保护整个业务操作，ConcurrentHashMap 提供更细的并发能力；跨键事务仍需另外设计。

**🔎 追问演练**：把变量声明为 volatile HashMap 就够了吗？

**推演要点**：只保障该引用的相关发布与可见性，不会让内部所有字段操作和复合更新自动原子化。

**原理展开**：[集合框架原理对应章节](集合框架原理.md#c-14)。

<a id="q-08"></a>
### Q8：LinkedHashMap 怎样做 LRU？

> **一句话结论**：访问顺序模式把近期访问节点移动到尾部，再用淘汰策略移除最老入口。

**机制展开**：哈希结构负责定位，双向链接负责顺序；访问顺序下 get 可能改变链接，迭代期间同线程访问也可能触发结构检查。

**⚖️ 方案对比与代价**：简单 LRU（Least Recently Used，最近最少使用）适合局部需求；过期、权重、并发加载、刷新和统计不是一个 removeEldestEntry 就能完整解决。

**🔎 追问演练**：为什么多个线程只调用 get 也未必安全？

**推演要点**：访问顺序 Map 的 get 可能修改结构；“语义上读取”与“实现上只读”不同。

**原理展开**：[集合框架原理对应章节](集合框架原理.md#c-08)。

<a id="q-09"></a>
### Q9：TreeMap 的键相等与 HashMap 相同吗？

> **一句话结论**：TreeMap 以比较结果为零识别同一键，HashMap 依据哈希与 equals。

**机制展开**：红黑树按比较关系组织，支持范围、前驱与后继；比较器必须满足传递性等要求，否则树的搜索前提会崩溃。

**⚖️ 方案对比与代价**：哈希适合精确定位，树适合有序范围；自然顺序通常不接受 null，自定义比较器能否接受需看实现逻辑。

**🔎 追问演练**：比较器直接 return a-b 有什么风险？

**推演要点**：整数溢出可反转符号，破坏顺序；用 Integer.compare，并检查 compare==0 与 equals 的一致性。

**原理展开**：[集合框架原理对应章节](集合框架原理.md#c-09)。

<a id="q-10"></a>
### Q10：WeakHashMap 能做可靠缓存吗？

> **一句话结论**：不能把弱键回收当成容量与过期策略，也不能忽略值对键的强引用。

**机制展开**：弱引用只改变部分可达性关系，条目清理还关联引用队列处理；如果值强引用键，键可能仍沿 Map→值→键保持强可达。

**⚖️ 方案对比与代价**：它适合特定元数据关联场景；可靠缓存还需要容量、淘汰、时间、并发和加载失败策略。

**🔎 追问演练**：为什么把键设为弱引用后占用仍不降？

**推演要点**：先画引用链，再分析收集与清理时机；不要把 GC（Garbage Collection，垃圾回收）当作实时定时器。

**原理展开**：[集合框架原理对应章节](集合框架原理.md#c-10)。

<a id="q-11"></a>
### Q11：PriorityQueue 遍历为什么没有排序？

> **一句话结论**：堆只保证堆顶最优和局部父子关系，没有承诺迭代器按优先级输出。

**机制展开**：peek 取顶通常 O(1)，插入和弹出通常 O(log n)，按对象查找或删除仍可能线性。需要顺序输出时逐个 poll 或复制后排序。

**⚖️ 方案对比与代价**：堆比完整排序更适合持续取最优元素；同优先级不自动先进先出，修改元素优先级也不会自动重建堆。

**🔎 追问演练**：任务优先级改了为何仍先执行旧优先级？

**推演要点**：队列不知道元素字段发生变化；移除后重插或用不可变队列记录，并明确相同优先级的次序键。

**原理展开**：[集合框架原理对应章节](集合框架原理.md#c-11)。

<a id="q-12"></a>
### Q12：不可修改集合就是不可变对象吗？

> **一句话结论**：不可修改接口只限制经该入口改变结构，既不必然隔离源变化，也不保证元素深度不可变。

**机制展开**：unmodifiableList 是包装视图；new ArrayList 是浅复制；List.of/copyOf 产出不可修改集合，但元素引用仍可指向可变对象。

**⚖️ 方案对比与代价**：包装成本低但共享源状态；复制隔离后续结构修改却消耗空间；深复制必须定义对象图和共享语义。

**🔎 追问演练**：用 unmodifiableList 包住内部列表后，原列表还能改变返回结果吗？

**推演要点**：能；包装器不是防御性副本。即使 copyOf 隔离了结构，内部可变元素仍需另外保护。

**原理展开**：[集合框架原理对应章节](集合框架原理.md#c-12)。

<a id="q-13"></a>
### Q13：Arrays.asList、subList 有什么坑？

> **一句话结论**：前者是数组支持的固定大小列表，后者是父列表的范围视图，都不等于独立可增长副本。

**机制展开**：asList 可 set 但不支持改变长度；int[] 作为单个泛型参数常得到只有一个数组元素的列表。subList 的修改回写父列表，父列表外部结构修改会使视图语义失效。

**⚖️ 方案对比与代价**：视图避免复制但共享状态和生命周期；长期持有很小的范围也可能保留整个后备存储。

**🔎 追问演练**：subList.clear 为什么删掉父列表的数据？

**推演要点**：其设计就是范围操作；若要独立处理，明确用 new `ArrayList<>`(subList) 复制结构。

**原理展开**：[集合框架原理对应章节](集合框架原理.md#c-12)。

<a id="q-14"></a>
### Q14：CME 是否说明一定有多个线程？

> **一句话结论**：不是，同一线程绕过迭代器修改结构也可能出现 ConcurrentModificationException（并发修改异常）。

**机制展开**：迭代器常用预期修改次数与结构修改次数比较；它是尽力检测，不是锁，也不是并发安全的证明。

**⚖️ 方案对比与代价**：iterator.remove/removeIf 适合受控删除；并发结构选择快照或弱一致语义，不能靠捕获异常循环重试维持正确。

**🔎 追问演练**：没有异常就能证明并发遍历安全？

**推演要点**：不能，检测并无必达保证；应根据实际所有权和同步关系证明，而非依赖症状。

**原理展开**：[集合框架原理对应章节](集合框架原理.md#c-13)。

<a id="q-15"></a>
### Q15：ConcurrentHashMap 的安全边界是什么？

> **一句话结论**：它提供并发访问和每键原子操作，不自动保护可变值与跨键不变量。

**机制展开**：现代实现组合原子更新、桶内协调和协助迁移，不应套用 JDK 7 的固定 Segment 模型。get 的非阻塞路径也不等于整个结构所有操作都无锁。

**⚖️ 方案对比与代价**：putIfAbsent/compute 代替先检查再写入；跨账户转账等业务需要额外同步或事务。

**🔎 追问演练**：`Map<String,List<?>>` 中的 List 自动线程安全吗？

**推演要点**：不；Map 安全发布了引用，不会把普通 ArrayList 变成并发容器。

**原理展开**：[集合框架原理对应章节](集合框架原理.md#c-14)。

<a id="q-16"></a>
### Q16：computeIfAbsent 是全局只执行一次吗？

> **一句话结论**：不是终身一次，它只在相应缺失映射的更新协议内计算，空结果、异常、移除都会改变后续行为。

**机制展开**：计算返回 null 不建立映射，抛异常也不会正常建立；函数应短小，避免递归修改同一 Map 及慢外部调用。

**⚖️ 方案对比与代价**：它适合原子建立条目；昂贵加载可缓存 Future 或采用专门缓存，但必须设计失败、过期和移除协议。

**🔎 追问演练**：为什么用户看见加载函数执行了两次？

**推演要点**：排查值是否被移除、函数是否返回 null/异常，以及两次观察是否属于不同建立周期。

**原理展开**：[集合框架原理对应章节](集合框架原理.md#c-14)。

<a id="q-17"></a>
### Q17：LongAdder 放入并发 Map 后一定精确吗？

> **一句话结论**：累加器能降低热点竞争，但结构安全、累加快照和条目生命周期是三件事。

**机制展开**：computeIfAbsent 建立累加器，再 increment；并发 sum 不等于跨所有分片的原子瞬时快照。拿到旧累加器后若条目被移除，后续增长可能不再出现在 Map 中。

**⚖️ 方案对比与代价**：指标统计可接受近似时优势明显；配额、序列号或结算需更强原子状态与生命周期协议。

**🔎 追问演练**：如何解释统计丢失却没有丢 increment？

**推演要点**：增量可能写入已脱离 Map 的旧对象，应追踪对象身份与移除竞争，而非只检查 increment 实现。

**原理展开**：[集合框架原理对应章节](集合框架原理.md#c-14)。

<a id="q-18"></a>
### Q18：CopyOnWriteArrayList 适合什么？

> **一句话结论**：适合写少、快照遍历可接受的场景，用写时复制换取读侧稳定视图。

**机制展开**：写入协调后复制数组并发布，新迭代器持有新数组，旧迭代器继续看旧数组；元素对象本身没有深复制。

**⚖️ 方案对比与代价**：写多时复制和内存压力大，长寿命迭代器保留旧数组；同步包装更适合需要共同锁保护的复合操作。

**🔎 追问演练**：先 contains 再 add 为什么仍重复？

**推演要点**：两个方法之间有竞争；用 addIfAbsent 或更高层协议，单方法安全不是组合原子。

**原理展开**：[集合框架原理对应章节](集合框架原理.md#c-15)。

<a id="q-19"></a>
### Q19：阻塞队列为什么需要显式容量？

> **一句话结论**：容量决定积压、内存和排队延迟的上限，线程安全不能替代过载控制。

**机制展开**：put/take 支持等待，offer/poll 可以立即或超时返回；SynchronousQueue 是交接不存储，LinkedBlockingQueue 默认容量极大不能据此认为实际有界。

**⚖️ 方案对比与代价**：有界队列把过载显式暴露给上游，无界队列隐藏过载直到延迟和内存失控；等待仍要有取消与关闭协议。

**🔎 追问演练**：内存队列取出成功代表任务处理成功吗？

**推演要点**：不代表，没有持久确认、重投和幂等协议；业务成功应单独记录。

**原理展开**：[集合框架原理对应章节](集合框架原理.md#c-16)。

<a id="q-20"></a>
### Q20：Stream.toList 与 Collectors.toList 一样吗？

> **一句话结论**：不一样，前者从 JDK 16 提供不可修改结果，后者不能依赖某个具体实现或可变性。

**机制展开**：toMap 还必须设计重复键的冲突处理，默认重复键会报错；要稳定顺序可显式指定合适 Map 工厂。

**⚖️ 方案对比与代价**：声明收集契约比依赖当前碰巧得到 ArrayList 更稳妥；并行流需用收集协议，不能无保护地向共享列表 add。

**🔎 追问演练**：parallelStream 配合 synchronizedList 就一定高效吗？

**推演要点**：互斥可能串行化热点，也不保证你需要的遭遇顺序；先证明语义，再测量合并与争用成本。

**原理展开**：[集合框架原理对应章节](集合框架原理.md#c-17)。

<a id="q-21"></a>
### Q21：JDK 21 的 Sequenced 集合解决什么？

> **一句话结论**：它统一表达明确遭遇顺序及首尾、反向视图能力，没有把所有集合变成任意插入的列表。

**机制展开**：SequencedCollection/Set/Map 为原有顺序能力补共同接口，reversed 通常是关联视图；排序结构必须保持排序约束，某些两端写操作可不支持。

**⚖️ 方案对比与代价**：业务可减少针对具体类的分支；升级前仍需检查最低运行版本及视图修改传播。

**🔎 追问演练**：reversed 后修改元素顺序会影响原集合吗？

**推演要点**：先判断返回的是视图还是副本，再看支持的操作；不要根据方法名字推断复制。

**原理展开**：[集合框架原理对应章节](集合框架原理.md#c-18)。

<a id="q-22"></a>
### Q22：如何验证集合性能而不误导？

> **一句话结论**：先验证语义与场景，再用基准工具控制预热、优化、数据规模和竞争，避免拿一次循环计时宣布赢家。

**机制展开**：比较包含定位、分配、扩容和真实访问分布；用 JMH（Java Microbenchmark Harness，Java 微基准测试工具）防止常见消除与预热偏差，另以应用压测观察尾延迟和堆占用。

**⚖️ 方案对比与代价**：微基准适合局部机制，业务负载还受数据库、网络和垃圾回收影响；结果只对所测条件负责。

**🔎 追问演练**：contains 总是 O(1) 的说法哪里错？

**推演要点**：必须说明集合实现、哈希分布、equals 成本与最坏情况；数据结构名称不能代替前提分析。

**原理展开**：[集合框架原理对应章节](集合框架原理.md#c-17)。

<a id="q-23"></a>
### Q23：CHM 扩容为什么不必停止全部读写？

> **一句话结论**：它以桶迁移和转发节点连接新旧表，不是全表持一把迁移锁。

**机制展开**：先发布目标桶再放旧桶转发标记，更新者检查迁移状态并重试，迁移区间可由多个线程领取。

**⚖️ 方案对比与代价**：降低集中停顿却增加每条访问路径的状态处理；跨键操作仍不是事务。

**🔎 追问演练**：get 看到 ForwardingNode 一定帮迁移吗？

**推演要点**：普通读取可沿 find 去新表，参与协助的是特定更新或协调路径。

**原理展开**：[集合框架深入机制](集合框架原理.md#c-19)。

<a id="q-24"></a>
### Q24：扩容时为什么要复查桶首？

> **一句话结论**：取得桶首引用后到真正协调成功之间，表槽位可能已经改变。

**机制展开**：复查当前槽位是否仍指向预期首节点，才能避免基于失效结构修改或迁移。

**⚖️ 方案对比与代价**：局部协调降低全局争用，但每次修改必须维护迁移协议。

**🔎 追问演练**：拿到旧节点的锁是否必然锁住当前桶？

**推演要点**：不是，要看表槽位是否仍以它为桶首，不能只凭锁对象相同判断结构身份。

**原理展开**：[集合框架深入机制](集合框架原理.md#c-19)。

<a id="q-25"></a>
### Q25：ConcurrentSkipListMap 为什么用跳表？

> **一句话结论**：分层有序链接把查找缩短为期望平均对数路径，局部维护有利并发实现。

**机制展开**：查找先横向再下降，底层定位键；删除可先逻辑失效再清理索引链接。

**⚖️ 方案对比与代价**：索引占内存且依赖分布，不能宣称所有查找严格最坏对数，也不提供范围事务快照。

**🔎 追问演练**：为什么不用 ConcurrentHashMap 完成同样范围查询？

**推演要点**：哈希结构没有维护键的全局排序，若要范围与前后键能力就需要不同结构。

**原理展开**：[集合框架深入机制](集合框架原理.md#c-20)。

<a id="q-26"></a>
### Q26：ConcurrentLinkedQueue 的 tail 不是最新值会丢入队吗？

> **一句话结论**：不会仅因 tail 暂时落后就丢失，元素由成功链接到链尾这一动作生效。

**机制展开**：tail 是可追赶的定位提示，其他线程能沿 next 前进；poll 也以 item 原子清空确定谁取走元素。

**⚖️ 方案对比与代价**：减少提示指针维护的强协调，换来遍历和重试成本；无界队列仍需外部容量控制。

**🔎 追问演练**：两个消费者先看见同一 item 会重复取出吗？

**推演要点**：只有成功完成相应 CAS 的消费者得到它，另一方必须重读状态。

**原理展开**：[集合框架深入机制](集合框架原理.md#c-20)。

<a id="q-27"></a>
### Q27：HashMap 树桶为什么不总能直接断言 O(log n)？

> **一句话结论**：树高为对数并不保证查找只走一条路径，键的哈希和可比较关系决定能否有效选择分支。

**机制展开**：先按 hash，再判断 equals，必要时使用可用的比较关系。同哈希且无法有效比较时，为避免漏掉引用不同但相等的键，某些路径可能探索多个子树。插入时的辅助排序不能简单当作查询时对任意相等对象都适用的业务排序。

**⚖️ 方案对比与代价**：树化抑制部分严重碰撞，但增加节点与维护成本；稳定且分布合理的键仍是首要条件。不能通过不合法的 compareTo 换取表面性能。

**🔎 追问演练**：扩容拆分与普通删除都在节点少于六时无条件退树吗？

**推演要点**：分别追踪入口。拆分有每侧计数，普通删除还有结构判断，常量不是完整算法。

**原理展开**：[树桶查找、退化与内存保留：从复杂度结论追到具体路径](集合框架原理.md#c-21)。
