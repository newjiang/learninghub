### Q1：注解为什么能实现事务？

> **一句话结论**：注解提供策略声明，事务框架读取后在实际执行入口建立事务边界。

**机制展开**：框架可能通过代理在调用前开启、之后提交或回滚；注解本身不执行数据库协议。

**⚖️ 方案对比与代价**：编译生成与运行代理是不同实现，成本与失效点也不同。

**🔎 追问演练**：有注解但内部调用不生效怎么解释？

**推演要点**：先确认调用是否经过代理，再查方法解析与配置，不能归因于注解被 JVM 忽略。

**原理展开**：[注解Annotation原理对应章节](注解Annotation原理.md#p-01)。

<a id="q-02"></a>
### Q2：Retention 默认值是什么？

> **一句话结论**：默认 CLASS，普通运行期反射通常需 RUNTIME。

**机制展开**：SOURCE 留源码阶段，CLASS 可供字节码工具读取，RUNTIME 才进入相应反射查询语义。

**⚖️ 方案对比与代价**：只按消费者需求保留，处理器也能处理 RUNTIME，不是一种策略对应一种消费者。

**🔎 追问演练**：CLASS 注解是否完全没有运行期用途？

**推演要点**：字节码工具仍可读取文件属性，区别在读取路线，不是文件里是否存在。

**原理展开**：[注解Annotation原理对应章节](注解Annotation原理.md#p-03)。

<a id="q-03"></a>
### Q3：@Inherited 能继承接口和方法注解吗？

> **一句话结论**：不能这样泛化，它只支持有限的类继承查询。

**机制展开**：接口标记不会自动出现在实现类上，覆写方法也不自动继承父方法标记。

**⚖️ 方案对比与代价**：框架可自行合并层次，但需定义优先级和冲突规则。

**🔎 追问演练**：Spring 查得到而 getAnnotation 查不到为什么？

**推演要点**：可能框架做了额外搜索、组合与合并，比较的是两套查找算法。

**原理展开**：[注解Annotation原理对应章节](注解Annotation原理.md#p-04)。

<a id="q-04"></a>
### Q4：重复注解怎样读取？

> **一句话结论**：用 ByType 系列按重复注解和容器规则读取。

**机制展开**：@Repeatable 指向容器，编译器可能把多个用法包装进容器；单注解查询不一定展开。

**⚖️ 方案对比与代价**：声明和容器必须符合目标与保留等约束，不能随意拼接。

**🔎 追问演练**：为什么明明写了两次却得到 null？

**推演要点**：检查实际存在形式与读取方法，别只查直接单个声明。

**原理展开**：[注解Annotation原理对应章节](注解Annotation原理.md#p-04)。

<a id="q-05"></a>
### Q5：TYPE_USE 和字段注解有何区别？

> **一句话结论**：前者标注类型使用位置，后者标注声明。

**机制展开**：List 中元素类型上的标记要通过 AnnotatedType 模型继续向内读取。

**⚖️ 方案对比与代价**：语义更精确，但消费者必须支持；自定义 NonNull 不会自动获得 JVM 校验。

**🔎 追问演练**：Field.getAnnotations 看不到元素非空标记怎么办？

**推演要点**：沿字段的 annotated type 进入参数化类型实参，确认 retention 与目标。

**原理展开**：[注解Annotation原理对应章节](注解Annotation原理.md#p-05)。

<a id="q-06"></a>
### Q6：注解处理器能修改所有方法体吗？

> **一句话结论**：标准处理模型主要读取声明并生成新文件，不保证任意改写现有语法树。

**机制展开**：Element/TypeMirror 建模符号，Filer 生成输出，后续轮次继续处理新源码。

**⚖️ 方案对比与代价**：依赖编译器内部 API 的 AST 修改更强但跨版本更脆弱。

**🔎 追问演练**：升级后注解生成突然停止怎么办？

**推演要点**：从 JDK 23 显式启用要求、处理器路径与实际 javac 参数查起。

**原理展开**：[注解Annotation原理对应章节](注解Annotation原理.md#p-06)。

<a id="q-07"></a>
### Q7：注解元素能用 List 或 null 吗？

> **一句话结论**：不可以，元素类型与值受语言规则限制。

**机制展开**：支持规定的基本类型、String、Class、枚举、注解及其一维数组；默认值也不能用 null。

**⚖️ 方案对比与代价**：有限类型便于 class 文件表示与静态校验，复杂可变配置宜另用对象。

**🔎 追问演练**：注解配置需要动态变化该怎么做？

**推演要点**：保留稳定声明，把动态值解析到显式配置源，而非修改内部注解代理。

**原理展开**：[注解Annotation原理对应章节](注解Annotation原理.md#p-02)。

<a id="q-08"></a>
### Q8：运行时注解一定就是某个代理类吗？

> **一句话结论**：应依赖 Annotation 契约，不应依赖具体内部表示。

**机制展开**：注解元素和 equals/hashCode 有专门值语义；数组内容也参与比较。

**⚖️ 方案对比与代价**：反射篡改内部字段既破坏语义又受模块封装约束，不是稳定更新接口。

**🔎 追问演练**：扫到注解对象就证明所有元素有效吗？

**推演要点**：不一定，类引用缺失或枚举变更等错误可能到访问具体元素时才抛出。

**原理展开**：[注解Annotation原理对应章节](注解Annotation原理.md#p-07)。

<a id="q-09"></a>
### Q9：注解扫描如何避免缓存泄漏？

> **一句话结论**：缓存要与加载器生命周期一致，不能只按名字永久保存 Class 和 Method。

**机制展开**：强引用反射对象可保留定义加载器；热部署后的同名类型还属于不同身份。

**⚖️ 方案对比与代价**：ClassValue 或作用域缓存可考虑，但仍要检查缓存值与外部注册关系。

**🔎 追问演练**：为什么清理 bean 后旧插件还在？

**推演要点**：沿缓存、线程、TCCL 和反射元数据查引用链，注解缓存也是持有者。

**原理展开**：[注解Annotation原理对应章节](注解Annotation原理.md#p-08)。

<a id="q-10"></a>
### Q10：注解处理器怎样让不存在的类在源码中可用？

> **一句话结论**：通过 Filer 生成新源码，让其在后续轮次进入编译模型。

**机制展开**：处理器先作为工具编译，应用处理轮次读 Element 并生成类型，最终编译包含生成源码。

**⚖️ 方案对比与代价**：生成减少运行期扫描，却增加构建输入与增量一致性责任。

**🔎 追问演练**：把处理器源码和业务源码放一起就一定生效吗？

**推演要点**：不能这样期待，工具必须已可加载，并显式配置发现和执行。

**原理展开**：[注解Annotation深入机制](注解Annotation原理.md#p-09)。

<a id="q-11"></a>
### Q11：为什么生成器不能随意覆盖同名文件？

> **一句话结论**：Filer 对同次创建和已有类型有约束，冲突应成为可诊断编译错误。

**机制展开**：来源元素与重复生成集合辅助追踪，但不能用覆盖隐藏命名冲突。

**⚖️ 方案对比与代价**：固定命名简单易追踪，全局聚合生成则有更多增量成本。

**🔎 追问演练**：SOURCE 注解运行期不可见，生成代码还能用吗？

**推演要点**：能，生成类已是普通编译产物，运行期不需要重新读取该 SOURCE 注解。

**原理展开**：[注解Annotation深入机制](注解Annotation原理.md#p-09)。

<a id="q-12"></a>
### Q12：为什么注解查找结果必须考虑目标类型？

> **一句话结论**：同一接口方法在不同实现类上可有不同覆写和注解。

**机制展开**：先定位业务方法并解析桥接，再按框架定义的来源与优先级合并。

**⚖️ 方案对比与代价**：只按接口 Method 缓存省事却可能跨实现错用策略，类型身份与生命周期都要进入设计。

**🔎 追问演练**：反射 getMethods 的顺序能决定注解覆盖吗？

**推演要点**：不能，应按明确规则排序和冲突校验，不依赖未承诺的遍历顺序。

**原理展开**：[注解Annotation深入机制](注解Annotation原理.md#p-10)。

<a id="q-13"></a>
### Q13：怎样知道注解元素是用户显式填写还是默认值？

> **一句话结论**：普通解析值未必保留足够信息，不能仅比较是否等于默认值来判断。

**机制展开**：显式填写一个等于默认的值，与省略元素后得到同值，在常规读取中可能无法区分。

**⚖️ 方案对比与代价**：需要逐元素覆盖时设计显式标志或特定元数据来源，简单整体覆盖更直观。

**🔎 追问演练**：多个组合注解冲突怎么办？

**推演要点**：预先规定优先级或编译/启动时报错，不能靠扫描先后碰运气。

**原理展开**：[注解Annotation深入机制](注解Annotation原理.md#p-10)。

<a id="q-14"></a>
### Q14：注解定义升级为什么也属于兼容性问题？

> **一句话结论**：旧使用点编码和当前元素声明共同决定运行期解释，默认值与必填元素变化都可能影响旧产物。

**机制展开**：省略元素可在读取时采用当前默认；显式编码的旧值则需符合新声明类型。引用类或枚举缺失等错误还可能到具体元素访问时才抛出。

**⚖️ 方案对比与代价**：新增兼容默认比修改类型容易迁移，但默认值也会改变业务行为。框架不能将解析失败等价成没有配置。

**🔎 追问演练**：为什么只做干净重编译测试会漏问题？

**推演要点**：真实部署可能混合旧使用者与新注解库，需要保留旧 class 验证二进制读取，而不是总让编译器先修正全部产物。

**原理展开**：[注解元数据的二进制演进：默认值、容器和类型变化](注解Annotation原理.md#p-11)。
