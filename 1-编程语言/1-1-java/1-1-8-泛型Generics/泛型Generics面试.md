<a id="q-01"></a>
### Q1：Java 泛型为什么不是运行时模板实例化？

> **一句话结论**：编译器检查参数化约束并主要通过擦除复用运行时类。

**机制展开**：必要强转和桥接补充语义，声明签名仍可供反射读取。

**⚖️ 方案对比与代价**：减少类复制并兼容旧代码，但限制基本类型实参和某些运行期检查。

**🔎 追问演练**：`List<String>` 与 `List<Integer>` 的 getClass 是否不同？

**推演要点**：通常同为同一个 List 实现类，不能据此恢复元素参数。

**原理展开**：[泛型Generics原理对应章节](泛型Generics原理.md#p-01)。

<a id="q-02"></a>
### Q2：`List<Integer>` 为什么不是 `List<Number>`？

> **一句话结论**：允许赋值就会允许写入 Double，破坏原列表约束。

**机制展开**：泛型不变阻止此类写入；数组协变则把类似错误留给运行期存储检查。

**⚖️ 方案对比与代价**：通配符能表达受限使用，而不是放弃类型安全。

**🔎 追问演练**：`List<?>` 与 `List<Object>` 相同吗？

**推演要点**：前者是某未知类型，后者明确能接受各种 Object，写入能力不同。

**原理展开**：[泛型Generics原理对应章节](泛型Generics原理.md#p-02)。

<a id="q-03"></a>
### Q3：PECS 怎么推导而非背口诀？

> **一句话结论**：看当前算法是从容器读 T，还是往容器写 T。

**机制展开**：extends 保证读出的上界，super 保证可写入的下界；未知实际类型决定反向操作的限制。

**⚖️ 方案对比与代价**：需要双向保持同一具体类型时可能应使用命名类型变量。

**🔎 追问演练**：extends 列表真的只能读吗？

**推演要点**：可有清空、删除或 null 写入等操作，且实际实现是否支持修改另有约束。

**原理展开**：[泛型Generics原理对应章节](泛型Generics原理.md#p-03)。

<a id="q-04"></a>
### Q4：类型参数与通配符怎样选？

> **一句话结论**：需要连接多个位置用命名变量，只表达某位置未知类型用通配符。

**机制展开**：推断从参数、目标和边界收集约束，不由运行时对象自动推断。

**⚖️ 方案对比与代价**：过度泛型会让调用和错误信息难懂，约束应有实际业务关系。

**🔎 追问演练**：static 方法能直接用类的 T 吗？

**推演要点**：不能，类 T 属于实例参数化语境，静态方法需自己的类型参数或显式类型。

**原理展开**：[泛型Generics原理对应章节](泛型Generics原理.md#p-04)。

<a id="q-05"></a>
### Q5：擦除一定擦成 Object 吗？

> **一句话结论**：不是，有界变量擦除为最左边界。

**机制展开**：擦除还影响方法签名，`List<String>` 与 `List<Integer>` 参数重载会冲突。

**⚖️ 方案对比与代价**：需区分可读源码签名、擦除签名和保留的 Signature 元数据。

**🔎 追问演练**：为什么返回类型不同也不能完成那种重载？

**推演要点**：Java 方法重载不能仅靠返回类型区分，擦除后参数也相同。

**原理展开**：[泛型Generics原理对应章节](泛型Generics原理.md#p-05)。

<a id="q-06"></a>
### Q6：桥接方法有什么用？

> **一句话结论**：让泛型覆写在擦除后的调用入口仍保持多态。

**机制展开**：编译器生成桥接方法转调具体实现，必要时转换参数或结果。

**⚖️ 方案对比与代价**：框架扫描须识别 bridge/synthetic，避免重复注册与注解误判。

**🔎 追问演练**：反射为何看见两个业务 get？

**推演要点**：检查一个是否编译器桥接，再映射实际覆写实现。

**原理展开**：[泛型Generics原理对应章节](泛型Generics原理.md#p-05)。

<a id="q-07"></a>
### Q7：为什么不能 new T[]？

> **一句话结论**：T 的具体运行期组件类型通常不可得，无法保证数组存储检查与静态约束一致。

**机制展开**：数组保留组件类型而多数参数化类型擦除，new `List<String>[]` 也因此不安全。

**⚖️ 方案对比与代价**：传入 Class 或数组工厂可以表达显式构建策略，不能靠 Object[] 强转通用解决。

**🔎 追问演练**：Object[] 强转 T[] 为什么在返回处炸？

**推演要点**：真实数组组件类型仍为 Object，调用方要求 String[] 时运行期转换失败。

**原理展开**：[泛型Generics原理对应章节](泛型Generics原理.md#p-06)。

<a id="q-08"></a>
### Q8：@SafeVarargs 是否保证安全？

> **一句话结论**：它是作者承诺，不能把不安全实现变安全。

**机制展开**：泛型 varargs 数组可能被别名或不兼容写入污染，错误常延后到读取发生。

**⚖️ 方案对比与代价**：审查数组是否逃逸、被写入或转交未知代码，再决定注解合理性。

**🔎 追问演练**：加了注解没有警告为何还会强转失败？

**推演要点**：警告被承诺压制不代表运行时检查消失，找最早的污染路径。

**原理展开**：[泛型Generics原理对应章节](泛型Generics原理.md#p-06)。

<a id="q-09"></a>
### Q9：泛型擦除后反射为何还有类型？

> **一句话结论**：声明签名可保留，但普通实例不携带每次构造的完整类型实参。

**机制展开**：ParameterizedType 等描述字段、父类或接口的声明结构，TypeVariable 可能仍未绑定。

**⚖️ 方案对比与代价**：类型令牌适合显式保留声明，不能神奇恢复任意 T。

**🔎 追问演练**：在泛型方法里匿名 `TypeRef<List<T>>` 能得知调用时 String 吗？

**推演要点**：通常仍得到 T，需要上下文替换或调用方传入具体 Type。

**原理展开**：[泛型Generics原理对应章节](泛型Generics原理.md#p-07)。

<a id="q-10"></a>
### Q10：如何定位泛型框架解析错误？

> **一句话结论**：沿继承路径建立并替换类型变量，保留未绑定信息而不是立即退成 Object。

**机制展开**：中间接口 T 与最终实体类型之间存在映射链，原始类型可能使信息真的丢失。

**⚖️ 方案对比与代价**：复杂解析需要诊断输出与显式令牌兜底，避免默默使用错误类型。

**🔎 追问演练**：为什么代理类上找不到实体参数？

**推演要点**：应回到目标声明与泛型父接口解析，代理运行时类不必保留相同声明路径。

**原理展开**：[泛型Generics原理对应章节](泛型Generics原理.md#p-08)。

<a id="q-11"></a>
### Q11：通配符捕获为什么能安全交换元素？

> **一句话结论**：辅助泛型方法为同一个未知元素类型引入一个局部名字 T。

**机制展开**：从 `List<T>` 读出的 T 写回同一 `List<T>` 保持类型约束，不需要把列表强转成 `List<Object>`。

**⚖️ 方案对比与代价**：捕获证明类型关系，不证明底层集合支持 set 或具备并发安全。

**🔎 追问演练**：List.of 传给类型正确的交换函数仍会怎样？

**推演要点**：可能因不可修改而抛异常，可修改性与类型安全是不同契约。

**原理展开**：[泛型Generics原理对应章节](泛型Generics原理.md#p-09)。

<a id="q-12"></a>
### Q12：为什么泛型父类中的实体 T 不能直接取出来就当 Class？

> **一句话结论**：它可能尚未绑定，也可能绑定为嵌套参数化类型而非单个 Class。

**机制展开**：沿继承路径建立声明变量到实参的映射，再递归替换字段与方法结构。

**⚖️ 方案对比与代价**：完整 Type 保留信息却增加处理复杂度，原始类型丢失时要有明确降级策略。

**🔎 追问演练**：Concrete 到 `Middle<String>` 再到 `Base<List<U>>`，T 是什么？

**推演要点**：在该上下文 T 是 `List<String>`，Base 的 `List<T>` 字段于是成为 `List<List<String>>`。

**原理展开**：[泛型Generics深入机制](泛型Generics原理.md#p-10)。

<a id="q-13"></a>
### Q13：泛型变量都按名字 T 缓存会怎样？

> **一句话结论**：不同声明中的同名变量会被错误合并。

**机制展开**：替换环境应按 TypeVariable 的声明身份和上下文建模，还要防递归边界无限展开。

**⚖️ 方案对比与代价**：字符串模型方便展示但不足以可靠表达真实类型身份。

**🔎 追问演练**：T extends `Comparable<T>` 是否该一直解析到 Class？

**推演要点**：不应无限递归，保留边界与未绑定变量，必要时要求显式类型令牌。

**原理展开**：[泛型Generics深入机制](泛型Generics原理.md#p-10)。

<a id="q-14"></a>
### Q14：ClassCastException 在桥接方法里是否说明编译器有错？

> **一句话结论**：通常要先查是否经原始类型或未检查入口传入错误参数。

**机制展开**：桥接适配擦除入口，参数强转揭露不符合具体实现约束的值。

**⚖️ 方案对比与代价**：应修最早污染路径，不能删除泛型约束或把全部读取改 Object。

**🔎 追问演练**：accept(Object) 明明接受 Integer 为什么失败？

**推演要点**：它可能是转调 accept(String) 的桥接入口，Object 只是擦除描述。

**原理展开**：[泛型Generics深入机制](泛型Generics原理.md#p-11)。

<a id="q-15"></a>
### Q15：反射给 `List<String>` 字段赋 `List<Integer>` 会立即拒绝吗？

> **一句话结论**：不一定，运行期字段类型检查主要看到 List，元素参数需另行验证。

**机制展开**：声明 Signature 可供解析器读取，但不会自动变成每次 Field.set 的深度检查。

**⚖️ 方案对比与代价**：框架需要结合上下文 Type 递归转换与校验，成本与错误策略都要明示。

**🔎 追问演练**：@SafeVarargs 能阻止数组别名污染吗？

**推演要点**：不能，它是作者承诺，数组逃逸与写入仍需审查。

**原理展开**：[泛型Generics深入机制](泛型Generics原理.md#p-11)。

<a id="q-16"></a>
### Q16：两个 List<?> 为什么不能随便交换元素？

> **一句话结论**：两个未知类型不保证相同，读出 Object 不提供写入另一未知类型的资格。

**机制展开**：问号表达存在某个类型，不是 Object 的别名。捕获辅助方法能命名同一次未知类型，维持同一列表读写关系，却不能凭空把两个独立捕获变量认定为一致。

**⚖️ 方案对比与代价**：上下界按实际方向提供弹性，命名类型变量建立跨位置联系；过度使用 raw type 只是推迟错误。运行期 checked 包装也只覆盖特定入口和可表达的 Class 检查。

**🔎 追问演练**：copy 编译通过就一定执行成功吗？

**推演要点**：还要满足 add 支持、null 与重复约束、容量、同步和生命周期，泛型不能替代这些契约。

**原理展开**：[从安全复制函数推导方差、捕获与运行期校验](泛型Generics原理.md#p-12)。
