<a id="q-01"></a>
### Q1：BIO、NIO、AIO 怎么区分？

> **一句话结论**：分别常指阻塞调用、Java 通道缓冲与多路复用体系、异步完成接口，但不是单一互斥分类。

**机制展开**：NIO 的 Channel 不都非阻塞，Selector 报就绪，异步回调报完成，虚拟线程又是执行模型。

**⚖️ 方案对比与代价**：先按数据、等待、通知和执行者四个维度比较，避免名词替代机制。

**🔎 追问演练**：FileChannel 是不是天然非阻塞？

**推演要点**：不能这样说，它属于 NIO 库却不等于可注册 Selector 的非阻塞网络通道。

**原理展开**：[IO原理对应章节](IO原理.md#p-01)。

<a id="q-02"></a>
### Q2：为什么逐块 new String 会乱码？

> **一句话结论**：一次 read 可以切开多字节编码，独立解码丢掉跨块状态。

**机制展开**：持续 Reader/CharsetDecoder 会保留未完成序列，手工处理需保留尾字节并按状态收尾。

**⚖️ 方案对比与代价**：整文件解码简单但内存高，增量解码需要正确状态机。

**🔎 追问演练**：一个 char 是否等于一个 Unicode 字符？

**推演要点**：不一定，char 是 UTF-16 代码单元，补充字符可需要代理对。

**原理展开**：[IO原理对应章节](IO原理.md#p-02)。

<a id="q-03"></a>
### Q3：flush、close、force 有何区别？

> **一句话结论**：分别涉及缓冲推进、资源释放和特定持久化要求，不能一概等同落盘。

**机制展开**：flush 往下游推数据，close 通常传播关闭，FileChannel.force 涉及存储同步且受平台契约约束。

**⚖️ 方案对比与代价**：资源谁拥有决定谁关闭，借入流不能擅自关闭调用方资源。

**🔎 追问演练**：flush 后对端一定处理完了吗？

**推演要点**：没有应用确认就不能证明，对端接收与业务完成另有协议。

**原理展开**：[IO原理对应章节](IO原理.md#p-03)。

<a id="q-04"></a>
### Q4：flip、clear、compact 怎么用？

> **一句话结论**：flip 转读已有范围，clear 准备重写，compact 保留未读尾部再续写。

**机制展开**：它们改变 position/limit 等状态，clear 不是把所有字节擦成零。

**⚖️ 方案对比与代价**：半包需保留尾部，slice/duplicate 共享底层数据不能当深复制。

**🔎 追问演练**：没读完就 clear 会怎样？

**推演要点**：逻辑上放弃未读范围，后续写入可覆盖待处理数据。

**原理展开**：[IO原理对应章节](IO原理.md#p-04)。

<a id="q-05"></a>
### Q5：直接缓冲一定比堆缓冲好吗？

> **一句话结论**：不一定，它可减少部分本地交互复制，却有更贵分配与本地内存管理成本。

**机制展开**：直接缓冲不走普通堆数组路径，仍可能有应用复制和内核工作。

**⚖️ 方案对比与代价**：适当复用有利高频 I/O，过量池化会保留峰值；测量真实大小与寿命。

**🔎 追问演练**：堆平稳但进程内存涨怎么查？

**推演要点**：同时看直接内存、映射、线程栈和本地库，而不只看 Java 堆。

**原理展开**：[IO原理对应章节](IO原理.md#p-05)。

<a id="q-06"></a>
### Q6：Selector 为什么不是完成通知？

> **一句话结论**：它告诉应用可尝试推进，真正读写仍由应用执行。

**机制展开**：read/write 可部分完成，read=0 与 read=-1 不同；协议状态须保留。

**⚖️ 方案对比与代价**：少量线程管理多连接，但慢业务不能占住事件循环。

**🔎 追问演练**：没有待写数据仍关注 OP_WRITE 会怎样？

**推演要点**：可写事件持续就绪，导致空转，应有积压才关注、写完移除。

**原理展开**：[IO原理对应章节](IO原理.md#p-06)。

<a id="q-07"></a>
### Q7：TCP 粘包怎样解决？

> **一句话结论**：先定义消息帧，按字节流逐步解析，而不是期待一次 write 对应一次 read。

**机制展开**：长度前缀要攒齐头、验证长度上限再读取体，分隔符要转义。

**⚖️ 方案对比与代价**：定长简单却浪费空间，变长更灵活但解析和资源防护复杂。

**🔎 追问演练**：对方声明 2GB 长度能直接分配吗？

**推演要点**：不能，先校验协议和业务上限，限制连接与全局缓冲。

**原理展开**：[IO原理对应章节](IO原理.md#p-07)。

<a id="q-08"></a>
### Q8：异步 I/O 底层一定不占线程吗？

> **一句话结论**：没有这种通用保证，提供者和平台可用不同实现。

**机制展开**：回调/Future 是接口完成语义，文件异步也可能由线程池执行阻塞操作。

**⚖️ 方案对比与代价**：选择模型看代码复杂度、并发量与平台能力，异步期间缓冲不能随便复用。

**🔎 追问演练**：异步写提交后马上改缓冲安全吗？

**推演要点**：操作完成前可能仍使用该缓冲，应按通道契约保持其生命周期和独占。

**原理展开**：[IO原理对应章节](IO原理.md#p-08)。

<a id="q-09"></a>
### Q9：虚拟线程会取代所有 NIO 吗？

> **一句话结论**：不会，它简化阻塞式并发，但协议与缓冲、下游容量仍存在。

**机制展开**：等待可让出载体，计算和外部资源仍有上限；特定本地调用也有约束。

**⚖️ 方案对比与代价**：顺序代码更清晰，事件循环与异步完成仍适合部分框架和场景。

**🔎 追问演练**：百万等待连接为何仍可能 OOM？

**推演要点**：线程更轻不等于零内存，缓冲、上下文和在途请求仍会堆积。

**原理展开**：[IO原理对应章节](IO原理.md#p-08)。

<a id="q-10"></a>
### Q10：零拷贝究竟零在哪里？

> **一句话结论**：通常指减少特定用户态与内核态复制，不是数据完全不移动。

**机制展开**：transferTo、mmap、直接缓冲优化不同路径，平台、短传输和加密都会改变效果。

**⚖️ 方案对比与代价**：需要内容变换时未必能保留原收益，性能结论须限定路径。

**🔎 追问演练**：transferTo 一次返回能当整文件完成吗？

**推演要点**：不行，要根据实际传输数推进并处理零进展和失败。

**原理展开**：[IO原理对应章节](IO原理.md#p-10)。

<a id="q-11"></a>
### Q11：mmap 后关闭 channel 会解除映射吗？

> **一句话结论**：不保证，已有映射有独立生命周期。

**机制展开**：访问映射会缺页并占地址空间，文件修改、截断与平台差异也需考虑。

**⚖️ 方案对比与代价**：适合特定随机访问，不能把它当免费且立即可释放的巨大数组。

**🔎 追问演练**：映射写入是否就是多文件事务？

**推演要点**：不是，持久化、原子性和崩溃恢复仍要另外设计。

**原理展开**：[IO原理对应章节](IO原理.md#p-10)。

<a id="q-12"></a>
### Q12：怎样排查写完文件却丢数据？

> **一句话结论**：先明确成功到应用缓冲、内核缓存还是持久存储哪一层。

**机制展开**：flush、force、原子移动与目录恢复各解决不同问题，存储和平台还有边界。

**⚖️ 方案对比与代价**：建立可恢复格式、校验与崩溃协议，比只调用一次 close 更可靠。

**🔎 追问演练**：rename 是否保证所有断电场景安全？

**推演要点**：不能跨平台泛化，还要核对文件系统、同步与目录持久化语义。

**原理展开**：[IO原理对应章节](IO原理.md#p-09)。

<a id="q-13"></a>
### Q13：Java 原生反序列化能直接用在外部输入吗？

> **一句话结论**：不应直接接受不受信任对象流。

**机制展开**：对象图构造与可执行回调带来攻击面，过滤可限制类型与规模但不是全部业务验证。

**⚖️ 方案对比与代价**：显式数据协议更便于限制、兼容和审计，也需要长度与字段校验。

**🔎 追问演练**：Files.lines 返回后不关流会怎样？

**推演要点**：可能保留文件资源，按契约在作用域中关闭，不能把它当纯内存集合。

**原理展开**：[IO原理对应章节](IO原理.md#p-11)。

<a id="q-14"></a>
### Q14：epoll 一定 O(1) 且优于 poll 吗？

> **一句话结论**：不能无条件这样说，它减少某些大集合重复维护与扫描，但就绪处理和业务仍有成本。

**机制展开**：持久兴趣集合与就绪集合适合大量空闲连接，注册、唤醒和返回事件都要执行工作。

**⚖️ 方案对比与代价**：高活跃率、任务粒度和平台差异可改变收益；Java Selector 不承诺全部平台同一实现。

**🔎 追问演练**：Reactor 与 Proactor 是两种内核调用吗？

**推演要点**：不是，它们是围绕就绪与完成的架构语义，底层可以由不同机制支持。

**原理展开**：[IO原理对应章节](IO原理.md#p-12)。

<a id="q-15"></a>
### Q15：长度前缀协议为什么需要每连接状态？

> **一句话结论**：输入可停在头或正文任意位置，后续读取必须继续同一帧。

**机制展开**：保存头部累积和剩余正文，先验证长度再分配；一次输入可反复交付多个完整帧。

**⚖️ 方案对比与代价**：简单整帧数组清晰但占内存，大帧和大量连接需全局预算与读取期限。

**🔎 追问演练**：读到 EOF 且剩半个正文能当正常结束吗？

**推演要点**：不能，该协议下是截断帧，应报告错误，除非协议另有明确允许。

**原理展开**：[IO深入机制](IO原理.md#p-13)。

<a id="q-16"></a>
### Q16：解析达到预算后能只等下一次 OP_READ 吗？

> **一句话结论**：不一定，剩余字节可能已在应用缓冲中，网络不会再为它们发事件。

**机制展开**：保留未消费输入并安排本地继续处理，避免 clear 丢数据或永久搁置。

**⚖️ 方案对比与代价**：每轮限额保护公平性，也要求事件循环管理本地可运行任务。

**🔎 追问演练**：只限制每帧 1MB 能防全部内存耗尽吗？

**推演要点**：不能，大量连接和多帧队列仍可累积，需要全局字节预算与背压。

**原理展开**：[IO深入机制](IO原理.md#p-13)。

<a id="q-17"></a>
### Q17：慢客户端为什么会把整个服务内存拖满？

> **一句话结论**：写入产生速度超过发送完成速度，待发送字节与业务响应持续积压。

**机制展开**：短写要保留缓冲，零进展应等待；单连接和全局都需字节预算与期限。

**⚖️ 方案对比与代价**：暂停上游能反馈压力，但协议若依赖读控制消息，盲停 OP_READ 可能形成死锁。

**🔎 追问演练**：只限制发送队列条数够吗？

**推演要点**：不够，消息大小不同，应同时限制字节、在途量和时间。

**原理展开**：[IO深入机制](IO原理.md#p-14)。

<a id="q-18"></a>
### Q18：通道关闭时哪些对象还可能泄漏？

> **一句话结论**：未发送缓冲、结果等待者、选择键附件与定时任务都可能仍被引用。

**机制展开**：统一状态机让正常排空、异常、取消进入同一幂等清理路径。

**⚖️ 方案对比与代价**：关闭一次通道不等于完成全部业务清理，资源所有权需明确。

**🔎 追问演练**：write 消费完缓冲是否说明对端业务成功？

**推演要点**：不说明，只完成了本地特定发送阶段，业务成功需协议确认。

**原理展开**：[IO深入机制](IO原理.md#p-14)。

<a id="q-19"></a>
### Q19：CharsetDecoder 返回 UNDERFLOW 为什么不能直接 clear 输入？

> **一句话结论**：它可能还有未消费的不完整编码前缀，clear 会使下次写入覆盖这些字节。

**机制展开**：非结束阶段用 compact 保留尾部再补输入；输出 OVERFLOW 要先消费输出再继续；真正结束还需 endOfInput=true 和 flush，才能正确报告末尾截断或输出内部状态。

**⚖️ 方案对比与代价**：整段读完再转字符串简单，但内存与延迟高；增量解码更节省资源，却需要完整状态机和错误策略。业务帧与字符编码仍是不同边界。

**🔎 追问演练**：帧结束但有半个字符，可以留给下一帧吗？

**推演要点**：先看协议是否规定每帧独立文本。若独立，应该报截断而不是跨帧拼接；持续文本流才按约定延续解码状态。

**原理展开**：[增量字符解码状态机：从字节边界到字符边界](IO原理.md#p-15)。
