### Q1：volatile 能替代锁吗？

> **一句话结论**：它适合可见性与发布，不能直接保护复合不变量。

**机制展开**：volatile 写读建立相应同步关系，但 count++ 仍是读、计算、写回。两个线程可以读取相同旧值。

**⚖️ 方案对比与代价**：小状态可用原子类，多字段可用同一锁；不用把所有变量都声明 volatile。

**🔎 追问演练**：为什么 volatile 库存仍超卖？

**推演要点**：列出两个线程都读到 1 的交错，再检查“判断并扣减”有没有作为整体原子执行。

**原理展开**：[锁机制原理对应章节](锁机制原理.md#p-02)。

<a id="q-02"></a>
### Q2：synchronized 到底锁什么？

> **一句话结论**：实例方法锁 this，静态方法锁声明类的 Class，同步块锁表达式得到的对象。

**机制展开**：互斥依据对象身份；不同实例、不同锁字段或替换后的对象都可能形成不同同步域。

**⚖️ 方案对比与代价**：封闭的 final 锁对象便于保持协议，公开对象锁可能被外部代码干扰。

**🔎 追问演练**：实例同步方法能和静态同步方法互斥吗？

**推演要点**：通常不能，它们持有不同对象；必须先画出实际锁身份。

**原理展开**：[锁机制原理对应章节](锁机制原理.md#p-03)。

<a id="q-03"></a>
### Q3：锁一定依次偏向、轻量、重量吗？

> **一句话结论**：不是，这是带版本和配置前提的历史实现描述。

**机制展开**：偏向锁在 JDK 15 默认禁用并在后续移除，现代轻量锁也不同于旧栈锁，监视器还能消胀。

**⚖️ 方案对比与代价**：理解快速路径、自旋和阻塞的成本更可迁移；对象头位图要标明源码版本。

**🔎 追问演练**：为何老调优参数在新 JDK 不可用？

**推演要点**：先核对选项的废弃、删除与实现演进，不把旧资料当运行时事实。

**原理展开**：[锁机制原理对应章节](锁机制原理.md#p-04)。

<a id="q-04"></a>
### Q4：ReentrantLock 一定比 synchronized 快吗？

> **一句话结论**：没有这种通用结论，应按能力需求和实际争用选型。

**机制展开**：前者支持超时、可中断获取与多个 Condition，后者结构化自动释放；两者都有现代优化。

**⚖️ 方案对比与代价**：显式锁增加释放遗漏风险，公平模式也可能降低吞吐。

**🔎 追问演练**：公平锁的 tryLock 会排队吗？

**推演要点**：无参 tryLock 可以插队；公平保证与方法入口、调度公平须分别讨论。

**原理展开**：[锁机制原理对应章节](锁机制原理.md#p-05)。

<a id="q-05"></a>
### Q5：AQS 的核心是什么？

> **一句话结论**：它把同步状态和等待协调做成框架，由子类解释获取与释放。

**机制展开**：原子状态变更失败后入队、检查、阻塞，释放后唤醒后继重新竞争；共享模式还需传播。

**⚖️ 方案对比与代价**：state 可代表重入计数或许可，不能固定说成布尔锁；字段名也不是稳定接口。

**🔎 追问演练**：被 unpark 后是否立即持锁？

**推演要点**：不是，唤醒只提供竞争机会；需要重新判断状态。

**原理展开**：[锁机制原理对应章节](锁机制原理.md#p-06)。

<a id="q-06"></a>
### Q6：为什么 await 必须用 while？

> **一句话结论**：唤醒不保证业务条件仍成立，还可能虚假唤醒。

**机制展开**：await 释放对应锁，返回前重获；其他线程可能先消费条件。检查和等待须在同一锁协议内。

**⚖️ 方案对比与代价**：if 省掉重检却丢失正确性，多 Condition 可减少无效唤醒但更需清晰状态设计。

**🔎 追问演练**：signal 后等待者会立即运行吗？

**推演要点**：发送者还持锁；等待者需被调度并重新获取锁，不能依赖直接交棒。

**原理展开**：[锁机制原理对应章节](锁机制原理.md#p-07)。

<a id="q-07"></a>
### Q7：wait、sleep、park 的区别？

> **一句话结论**：它们释放锁、准入检查和唤醒机制各不相同。

**机制展开**：wait 释放目标监视器；sleep 不释放锁；park 基于许可并可无原因返回，不自动释放业务锁。

**⚖️ 方案对比与代价**：高层 Condition 或队列通常更易证明，直接 park 需自己处理状态检查、发布和取消。

**🔎 追问演练**：持锁 sleep 为什么导致其他线程卡住？

**推演要点**：线程虽暂不执行，但所有权仍保留；等待时长不是释放锁的条件。

**原理展开**：[锁机制原理对应章节](锁机制原理.md#p-07)。

<a id="q-08"></a>
### Q8：CAS 为什么有 ABA 问题？

> **一句话结论**：比较当前值不能表达期间是否发生过变化。

**机制展开**：A 经 B 回到 A，旧观察者 CAS 仍可能成功；若算法依赖代际或节点历史就可能错误。

**⚖️ 方案对比与代价**：版本戳增加状态信息，也要考虑回绕；若只关心当前数值，ABA 未必是问题。

**🔎 追问演练**：重试函数里发消息会怎样？

**推演要点**：失败后重跑可能重复发送；先区分纯状态计算和不可撤销副作用。

**原理展开**：[锁机制原理对应章节](锁机制原理.md#p-08)。

<a id="q-09"></a>
### Q9：读写锁如何升级和降级？

> **一句话结论**：读到写通常要先释放再获取并重检，写到读可按协议降级。

**机制展开**：持读锁等待写锁可能被自己阻止；释放读锁后状态可变，写锁到手后必须重新判断。

**⚖️ 方案对比与代价**：读写锁有协调成本，短小读取可能不如简单互斥；不要只按读比例判断。

**🔎 追问演练**：为什么双线程同时升级容易死锁？

**推演要点**：两者都保留读持有又等待独占写，互相阻挡写者所需的读者清零。

**原理展开**：[锁机制原理对应章节](锁机制原理.md#p-09)。

<a id="q-10"></a>
### Q10：StampedLock 乐观读怎样写才正确？

> **一句话结论**：先读候选值到局部变量，再验证，失败后持读锁重读。

**机制展开**：stamp 用于验证读取区间有没有冲突，不能让后续所有读取自动安全；其锁不支持重入。

**⚖️ 方案对比与代价**：乐观路径降低读协调，但复杂对象图可能在验证前就发生非法访问，需要限制读操作。

**🔎 追问演练**：validate 后再读字段可以吗？

**推演要点**：后读不在已经验证的区间内，可能再次遇到写者；应使用已读取的局部值。

**原理展开**：[锁机制原理对应章节](锁机制原理.md#p-09)。

<a id="q-11"></a>
### Q11：虚拟线程下还要避免 synchronized 吗？

> **一句话结论**：须按版本判断，不能延续 JDK 21–23 的固定问题结论到所有新版本。

**机制展开**：JDK 24 改进了监视器相关固定，虚拟线程仍要竞争锁，也受本地调用和下游资源限制。

**⚖️ 方案对比与代价**：改显式锁应因为需要其能力或有测量证据，不能机械替换；大量等待者不等于业务容量提升。

**🔎 追问演练**：一万个虚拟线程能让单锁计数线性加速吗？

**推演要点**：临界区仍串行，瓶颈是共享状态与锁持有时间，线程便宜不改变串行比例。

**原理展开**：[锁机制原理对应章节](锁机制原理.md#p-10)。

<a id="q-12"></a>
### Q12：如何排查死锁与长等待？

> **一句话结论**：构建等待图并追踪状态推进，而非只看一个 BLOCKED 字样。

**机制展开**：多次线程转储区分稳定等待环和暂时慢调用，记录线程持有哪把锁又等待谁。

**⚖️ 方案对比与代价**：统一锁顺序更根本，超时只提供退出机会，还要处理恢复和副作用。

**🔎 追问演练**：线程都活着并且不断重试，为什么服务不进展？

**推演要点**：可能是活锁或过载重试，查看成功率与推进指标而非只看线程存活。

**原理展开**：[锁机制原理对应章节](锁机制原理.md#p-10)。

<a id="q-13"></a>
### Q13：双重检查锁定为什么要 volatile？

> **一句话结论**：快速路径没有持锁，必须用明确发布协议让它观察到构造结果。

**机制展开**：第一次检查减开销，锁内复查防重复创建，volatile 写读发布对象构造状态。

**⚖️ 方案对比与代价**：静态持有者更简单但初始化失败与类生命周期绑定；需要重试和热更新时应显式建状态协议。

**🔎 追问演练**：引用是 volatile，对象所有字段以后都安全吗？

**推演要点**：只保证相关发布链，后续可变字段仍需同步；构造时泄露 this 也要修复。

**原理展开**：[锁机制原理对应章节](锁机制原理.md#p-11)。

<a id="q-14"></a>
### Q14：缓存一致性为什么不能保证 count++ 安全？

> **一句话结论**：它不把读、计算、写回三个动作合成一次不可分割的状态转换。

**机制展开**：两线程可各自合法读到旧值并写相同新值，最终丢一次更新；可见性与复合原子性不同。

**⚖️ 方案对比与代价**：原子类适合单状态转换，锁适合多个字段的不变量，不能凭硬件协议名字替代同步设计。

**🔎 追问演练**：加 volatile 后为什么还会丢更新？

**推演要点**：它约束相关读写和发布，但自增仍是多步骤，须使用原子更新或共同锁。

**原理展开**：[锁机制深入机制](锁机制原理.md#p-12)。

<a id="q-15"></a>
### Q15：发布标记读到了，数据一定可靠吗？

> **一句话结论**：要检查写入先于发布、读取后于获取，以及是否还有后续无同步修改。

**机制展开**：一次发布可由先行发生链证明，先读数据后读标记或重复复用标记不能直接沿用同一证明。

**⚖️ 方案对比与代价**：不可变快照使证明简单，原地重复更新需要额外版本或锁。

**🔎 追问演练**：为什么 ready 为 true 仍读到旧局部变量？

**推演要点**：局部变量若在读取 ready 前已取值，后面的同步不会追溯修改那次读取。

**原理展开**：[锁机制深入机制](锁机制原理.md#p-12)。

<a id="q-16"></a>
### Q16：signal 之后线程为什么还不继续？

> **一句话结论**：它还可能等待发送者释放锁、等待调度，并在同步队列重新竞争。

**机制展开**：条件等待集合不等于锁所有权，转移后要重获并复查谓词。

**⚖️ 方案对比与代价**：多条件可减少无效唤醒，但需要精确证明通知对象和关闭策略。

**🔎 追问演练**：被唤醒后条件又没了怎么办？

**推演要点**：while 重新等待，通知是进展机会而非独占领取凭证。

**原理展开**：[锁机制深入机制](锁机制原理.md#p-13)。

<a id="q-17"></a>
### Q17：await 竞争中断和 signal 时能固定预测结果吗？

> **一句话结论**：不能只凭外部日志时刻推断，节点转移与取消竞争决定具体路径。

**机制展开**：实现需保证重获锁并按契约处理抛错或恢复中断，业务应同时检查退出与资源状态。

**⚖️ 方案对比与代价**：依赖成熟 Condition 协议，不能用简单 park 模仿全部取消竞争。

**🔎 追问演练**：为什么定时等待要重新计算剩余预算？

**推演要点**：重新完整计时会在多次唤醒后超过原本截止时间。

**原理展开**：[锁机制深入机制](锁机制原理.md#p-13)。

<a id="q-18"></a>
### Q18：自定义 AQS 同步器时哪些逻辑不能交给框架猜？

> **一句话结论**：子类定义状态含义、合法获取释放和持有者规则，AQS 承担相应排队、取消与唤醒协调。

**机制展开**：独占锁要用原子转换防止两个线程同时获得资格，释放要校验身份并按正确顺序发布空闲。可重入计数未归零时，不能报告完全释放。不可重入实现还应明确同线程再次进入的行为。

**⚖️ 方案对比与代价**：复用 AQS 避免重写复杂等待算法，却不会自动获得公平、可重入或 Condition。普通业务应优先用成熟工具，自定义只在确有特殊协议时考虑。

**🔎 追问演练**：先 state=0，再清 owner 为什么危险？

**推演要点**：新线程可能在两步之间取得状态并成为持有者，随后旧线程又抹掉新 owner；把释放的发布点与归属更新顺序画出来即可定位错误。

**原理展开**：[从零构造 AQS 独占同步器：状态、不变量与失败路径](锁机制原理.md#p-14)。
