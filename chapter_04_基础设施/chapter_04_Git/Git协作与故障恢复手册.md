# Git 协作与故障恢复导读与速查

> 阅读定位：本篇是导读与速查，不代替深入正文。已展开专题和当前覆盖边界见[知识手册导航](../../知识手册导航.md)。

适用范围：Git 2.x。涉及历史重写或工作区覆盖的操作，先确认未提交文件和共享分支状态，并创建可恢复引用。

## 1. 对象、引用与三区

commit 记录树对象、父提交和元信息；branch 是可移动引用，HEAD 表示当前引用或游离提交。工作区、暂存区与提交是三个不同视图：`git diff` 看工作区相对暂存，`git diff --cached` 看暂存相对 HEAD。

提交前查看 `git status --short` 与两类 diff，避免把本地配置和密钥带入。`.gitignore` 只约束未跟踪内容，不会自动移除已跟踪文件或历史中的秘密。

## 2. 合并、变基和选择提交

merge 保留分支拓扑，rebase 将提交重新应用到新基线并生成新提交 ID。已共享分支随意 rebase 会让协作者基于旧历史继续工作；团队应约定哪些分支允许重写。

cherry-pick 适合有限补丁搬运，但重复搬运可能造成重复修改和难追踪来源。冲突解决应理解两边业务意图，不能仅选 ours/theirs。自动合并成功也需要验证语义，特别是接口与调用方分别变更的场景。

```bash
# 只读检查，适合开始排查时使用
git status --short
git log --oneline --graph -20
git diff
git diff --cached
git reflog -20
```

## 3. 恢复策略

已发布错误提交通常用 revert 创建反向提交，保留共享历史；revert merge 需要选主线，且会影响未来再次合并，先画清拓扑。reset 会移动引用，某些模式还会改暂存和工作区，不是通用撤销按钮。

reflog 记录本地引用移动，可帮助找回误移动的提交；找到目标后先建立新分支引用再做后续操作。reflog 不是永久备份，未提交且未保留的文件也不一定能靠它恢复。

stash 适合短期临时保存，默认不覆盖所有未跟踪文件；长期工作用明确提交和分支更可追踪。worktree 提供多个检出目录，仍共享仓库对象和部分引用管理，需要避免误解为完整独立副本。

## 4. 发布与协作

短分支、小提交和清晰描述降低审查负担。保护分支要求检查与审查通过，发布 tag 与制品关联到确切提交；数据库迁移、配置和应用制品共同定义可回滚版本。

误提交密钥时先撤销/轮换密钥，再处理历史与访问范围，删当前文件不能撤销已泄漏的凭据。force-with-lease 提供并发引用保护，仍是重写历史，不能把它理解为对共享分支完全安全。

## 5. 面试与练习

- **merge 与 rebase 怎么选？** 先说明团队历史策略、分支是否共享及审查需求，再讨论线性历史和可追溯性。
- **为什么回滚代码还不能恢复业务？** 外部副作用、数据格式和 schema 可能不可逆，需要兼容发布及补偿。
- **练习**：在临时仓库演示冲突、revert 和误移动分支恢复。验收：通过 reflog 建立恢复分支，未提交文件保留，解释每步前后三个视图的变化。
