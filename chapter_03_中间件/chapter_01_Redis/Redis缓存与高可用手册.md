# Redis 缓存与高可用导读与速查

> 阅读定位：本篇是导读与速查，不代替深入正文。已展开专题和当前覆盖边界见[知识手册导航](../../知识手册导航.md)。

基线：Redis 7.x 的常见数据结构、持久化及集群模型。不依赖特定商业模块；托管服务的持久化、故障切换和许可需独立核对。

## 1. 数据结构与执行模型

String 适合简单缓存、计数；Hash 适合字段集合；Set 做去重；Sorted Set 做有序排名；Stream 做带消费组的日志结构。选择要结合元素数、字段大小、访问模式和删除成本，不能只看逻辑类型。

主要命令执行路径按串行模型理解，但网络 I/O、持久化等可能有后台线程或进程，所以“Redis 完全单线程”不准确。慢命令、超大 key、全量遍历仍能阻塞服务；线上用 SCAN 渐进遍历，SCAN 可能返回重复元素，也不提供某个时刻的完整快照。

Pipeline 减少往返，不提供原子事务；MULTI/EXEC 不提供数据库式的错误回滚。Lua 脚本在执行期间具有隔离性，但写入后发生运行错误也不会自动撤销先前修改，逻辑必须先校验、后写入且控制耗时。

## 2. 缓存一致性与热点

Cache Aside 常用“读缓存，未命中查库后填充；写库成功后删除缓存”。并发读可能在删除后回填旧值，延迟双删只能缩小部分窗口。强一致读取应回源或设计版本校验；最终一致可用 CDC/outbox 失效、版本号及对账，必须定义允许陈旧时间。

| 问题 | 机制 | 工程方案 |
| --- | --- | --- |
| 穿透 | 请求不存在的数据反复回源 | 输入校验、短期负缓存、布隆过滤器及更新机制 |
| 击穿 | 热点 key 过期并发回源 | 单飞合并、逻辑过期、回源并发上限 |
| 雪崩 | 大量 key 同时失效或缓存不可用 | TTL 抖动、隔离限流、降级及容量预案 |
| 热 key | 单分片承载过多流量 | 本地只读缓存、热点拆分及一致性取舍 |

TTL 负责数据新鲜度的一部分，不会自动解决内存淘汰。maxmemory 策略可能造成非预期缓存丢失，不能把可淘汰缓存用作唯一业务事实来源。

## 3. 分布式锁及边界

```text
SET lock:order:123 <随机且本次唯一的token> NX PX 10000
```

解锁需要 Lua 原子比较 token 后删除；仅 DEL 可能删掉别人的锁。续租也要验证持有者，但长暂停、网络分区和租约过期仍可能让旧持有者继续执行。涉及不可重复的资源写入，需要下游验证单调递增 fencing token，或用数据库唯一约束/条件更新维护最终正确性。

不能把单节点租约锁宣传为任意故障下的强互斥；异步主从切换也有丢锁风险。锁是协调机制，不是业务幂等的替代品。

## 4. 持久化、复制与 Cluster

RDB 保存快照，恢复快但可能丢失快照后数据；AOF 记录写操作，丢失窗口和延迟取决于刷盘策略及系统。复制通常异步，主节点确认不意味着所有副本已经持久化。

Sentinel 负责主从监测和切换，不做数据分片；Cluster 通过槽位分片，跨槽多 key 操作受限，hash tag 可以共置相关 key，但也可能制造热点。客户端必须正确处理重定向与拓扑变化。

## 5. 排障、面试与练习

延迟升高先对齐客户端等待与服务端命令耗时，查看 SLOWLOG、延迟事件、big key、CPU、网络及持久化活动。SLOWLOG 不包含所有网络等待。内存看 used_memory、RSS、碎片及复制/AOF 缓冲，fork 时写时复制可能增加峰值。

- **“先删缓存再更新库”有什么问题？** 并发读取会在库更新前回填旧值；说明执行时序，而非背结论。
- **有锁为什么还超卖？** 租约、重复消息和锁粒度都可能失效，库存约束应在事实存储中保证。
- **练习**：模拟热点 key 过期、缓存全停及持锁线程暂停。验收：数据库回源并发有上限；订单不重复执行；恢复后能对账；陈旧数据时长可测量。
