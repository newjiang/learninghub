# Elasticsearch 搜索工程导读与速查

> 阅读定位：本篇是导读与速查，不代替深入正文。已展开专题和当前覆盖边界见[知识手册导航](../../知识手册导航.md)。

基线：Elasticsearch 8.x，API 与默认项以项目固定小版本为准。搜索索引通常是数据库的派生读模型，不承担所有业务事务。

## 1. 从倒排索引到分布式查询

倒排索引把词项映射到文档集合；text 经过分析器，keyword 适合精确匹配、排序和聚合。分词器选择影响召回与精度，中文词典、同义词及分析链要用真实查询验证，不能上线后只靠调分数补救。

索引分片包含 Lucene 索引，副本提升可用性和读承载。查询常有分片级执行与协调节点合并阶段，因此分片过多会增加扇出、堆和管理成本；分片过少也限制容量与恢复并行度。按数据量、写入速率、查询方式和恢复目标压测决定。

## 2. 映射与查询设计

```json
PUT orders_v1
{
  "mappings": {
    "dynamic": "strict",
    "properties": {
      "tenant_id": { "type": "keyword" },
      "order_id": { "type": "keyword" },
      "title": { "type": "text" },
      "created_at": { "type": "date" },
      "amount_cent": { "type": "long" }
    }
  }
}
```

示例用于隔离练习索引，尚未设置副本、分片和生命周期。filter 表达不计分条件，must/match 参与相关性语义；term 查询 text 字段经常与预期不同。数组对象需要保留对象内字段关联时考虑 nested，但其存储及查询成本更高。

动态映射可能导致字段爆炸和错误类型固定，关键业务字段显式定义。租户过滤由服务端强制注入，不由用户自由选择。

## 3. 刷新、可靠同步与重建

refresh 让已索引内容可被搜索，flush 与 translog/提交相关，不能混淆。近实时意味着写入成功后不一定立刻被搜索到；对特定交互可评估 refresh=wait_for，避免每次强制刷新降低吞吐。

用 outbox/CDC 同步派生索引，以文档 ID 实现覆盖写或去重，携带业务版本避免旧事件覆盖新数据。重建采用新版本索引、全量回灌、增量追平、校验和别名切换；回滚还要确认旧索引是否持续接收增量。

深分页用 PIT 配合 search_after 和稳定排序；需要管理 PIT 有效期及资源。大批量导出不等于在线用户分页，按独立任务处理并限流。

## 4. 排查、面试与练习

查询慢先看查询 profile/慢日志、分片大小、聚合基数、segment、磁盘和 JVM；profile 有额外开销，不应给所有生产请求开启。磁盘水位、分片未分配和写拒绝先查集群分配原因，再决定扩容或迁移，不能先删数据碰碰运气。

- **为什么不用数据库 LIKE？** 从分词召回、相关性、聚合和规模说明收益，同时承认同步延迟和运维成本。
- **索引为什么不能随意改类型？** 既有数据的编码及索引结构受映射约束，通常需要新索引重建。
- **练习**：构建订单搜索，从数据库回灌并接入增量。验收：重复、乱序事件不破坏最新版本；搜索强制租户过滤；别名切换前后总量及抽样字段一致，延迟可监测。
