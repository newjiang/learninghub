# MySQL 事务与性能实战补充

> 阅读定位：本篇是导读与速查，不代替深入正文。已展开专题和当前覆盖边界见[知识手册导航](../../知识手册导航.md)。

基线：MySQL 8.0/8.4、InnoDB。与现有 [MySQL 笔记](MySQL.md) 配合阅读；本章聚焦生产约束与易混淆结论。

## 1. 先纠正常见版本和模型误区

MySQL 8.0 已移除 Query Cache，不能再将它画作当前 SQL 执行的常规优化层。thread_cache_size 控制连接线程复用，不等于商业/特定发行版的线程池，也不存在普适的“CPU 核数乘二”最优值。

索引是写入、空间和查询的交换；联合索引按排序组织，最左前缀是理解基础，但优化器的范围访问、覆盖扫描、跳跃扫描等能力要结合版本与计划，避免“没走第一列必然完全不能用”的绝对判断。

## 2. 库存扣减与幂等

```sql
-- 片段：在同一本地事务内完成请求去重、扣减及订单写入。
-- 请求表 UNIQUE(tenant_id, request_id)，重复时查询并返回原结果。
UPDATE inventory
SET available = available - 1
WHERE sku_id = ? AND available >= 1;
-- 必须检查 affected rows = 1，失败则按库存不足处理。
```

“先 SELECT 库存，再无条件 UPDATE”在并发下可能超卖。条件更新将约束放到原子写入；多 SKU 固定锁顺序，减少死锁概率。去重键还要绑定参数摘要，拒绝相同键携带不同业务请求。

## 3. MVCC 与锁

一致性读通常读取符合 read view 的版本；锁定读/写操作使用不同访问规则。RR 下不能仅凭普通 SELECT 的快照推断后续 UPDATE 看到什么。间隙锁、next-key lock 的范围取决于隔离级别、索引和访问路径，不能简化为“RR 所有查询都锁表”或“有 MVCC 就不用锁”。

二级索引范围扫描与回表也可能增加锁范围。唯一索引精确定位、范围查询和未命中查询的锁行为不同。长事务保留旧版本并阻碍清理，还会增加锁持有与复制压力。

死锁是并发执行中可预期的结果。捕获数据库明确死锁错误后，按整体事务有限重试，保持幂等；仅重试最后一条 SQL 可能破坏先前业务判断。

## 4. 慢查询诊断流程

先取 SQL digest、频率、P95/P99 和扫描行数，避免只优化偶发最慢的一条。EXPLAIN 看连接顺序和估计，EXPLAIN ANALYZE 会执行查询并提供实际执行信息，不能对未知代价的生产查询随意使用。

分别判断连接池等待、锁等待、磁盘、CPU、网络和应用映射。覆盖索引减少回表，索引下推减少部分无用回表；filesort 不一定写磁盘，使用索引也不等于查询快。索引变更先验证目标查询及写入成本，再按部署能力控制锁和复制延迟。

## 5. 高可用与迁移

主从复制不保证写后立刻在任意副本可见。支付完成页可短期读主或通过应用一致性标记路由；读写分离需要延迟检测和降级。备份方案要定义 RPO/RTO，并验证全量备份与 binlog 的时间点恢复链路。

表结构迁移采用 expand-contract：先增加兼容字段/表，再双写或回填校验，切换读取，最后在回滚窗口后移除旧结构。应用回滚不一定能逆转不兼容 schema 变更。

## 6. 面试与练习

- **唯一索引能解决什么幂等？** 可以约束某个业务键只创建一次，不能直接保证跨支付等外部副作用只发生一次。
- **为什么连接池越大越慢？** 更多并发可能增加锁等待、上下文切换和数据库排队，需通过容量曲线定位拐点。
- **练习**：两个会话演示 RR 普通读、锁定读与死锁，再做库存并发测试。验收：库存不为负、同一幂等键结果一致、死锁重试有上限并保留诊断信息。
