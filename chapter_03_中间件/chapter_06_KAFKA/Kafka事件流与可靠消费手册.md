# Kafka 事件流与可靠消费导读与速查

> 阅读定位：本篇是导读与速查，不代替深入正文。已展开专题和当前覆盖边界见[知识手册导航](../../知识手册导航.md)。

基线：Kafka 3.9/4.x 的经典 consumer group 和分区日志模型；4.x 的控制平面使用 KRaft，旧版 ZooKeeper 部署经验不能直接照搬。新消费协议与 share group 不在本章默认模型内。

## 1. 分区、顺序与复制

topic 分成 partition，同一分区内有序，不保证跨分区全局顺序。经典消费组中一个分区同一时刻由组内一个消费者分配处理；业务自行并行后仍可能乱序完成。相同 key 的分区策略变化、分区数扩容都可能影响后续路由和顺序假设。

leader 提供分区读写，副本和 ISR 决定复制状态。生产端 acks=all 配合 min.insync.replicas 可以提高可靠性，但还需副本数、故障选举策略、重试及磁盘条件共同满足目标，不能简化为“绝不丢消息”。

## 2. 生产、消费与幂等

```text
业务数据库事务：插入订单 + 写 outbox(event_id, order_id, version, payload)
投递器：发送 Kafka；收到确认后标记投递；失败允许重新发送
消费者数据库事务：插入 inbox(consumer_name, event_id) 唯一键 + 执行业务更新
本地事务成功后：提交消费 offset
```

投递确认丢失和 offset 提交失败都可能造成重复。inbox 的去重记录必须和业务变更在同一事务中，不能先标记已处理再执行业务。去重保留周期要覆盖消息保留、重放和人工补偿窗口。

Kafka 的幂等 producer 处理特定生产重试重复，不能替代业务事件 ID。Kafka 事务可把 Kafka 读、处理、写和 offset 纳入对应事务范围，消费端需配合隔离级别；外部数据库、支付接口并不自动加入这个保证。

## 3. 重平衡、积压与顺序

消费者长时间不 poll 可能触发组成员失效，业务执行时长与 max.poll.interval 等配置需协调。将工作移交线程池要解决 offset 提交顺序：后面的消息完成不能证明前面的消息已成功。可按分区串行或维护连续完成位置。

积压先判断消费能力下降、生产突增、热点分区还是 poison message。单纯增加消费者超过分区数对经典组不增加并行度；扩分区又会影响 key 分配。重试 topic 提高隔离能力，但可能打破原分区业务顺序，必要时以业务版本控制。

## 4. 容量与排查

保留量粗估为每秒写入字节 × 保留秒数 × 副本数，再加索引、段、压缩差异和磁盘余量。吞吐调优同时观察批次、压缩、延迟及 broker 资源，不能只调大 batch.size。

关键指标包括生产错误/重试、ISR 缩减、未充分复制分区、请求时延、磁盘、消费 lag 及最老事件年龄。lag 是 offset 差时，不能直接当作秒数或精确业务数量；压缩 topic、不同分区速率会改变解释。

## 5. 面试与练习

- **Exactly once 能不能保证只扣一次款？** Kafka 内部范围不覆盖外部支付，需业务幂等键、结果查询和对账。
- **先提交 offset 会怎样？** 业务未成功却不再重投会丢处理；后提交会重复，所以要幂等。
- **练习**：在数据库提交后、offset 提交前终止消费者并重启。验收：消息重复但业务只生效一次；坏消息有重试上限和人工恢复入口；积压恢复期间不压垮数据库。
