# ZooKeeper 协调服务导读与速查

> 阅读定位：本篇是导读与速查，不代替深入正文。已展开专题和当前覆盖边界见[知识手册导航](../../知识手册导航.md)。

基线：ZooKeeper 3.9。用于低频、小数据协调，不能当作大规模业务数据仓库或高吞吐消息系统。

## 1. 数据模型和一致性边界

znode 形成层次命名空间，存少量数据与版本元信息。持久节点独立于会话存在；临时节点与会话绑定，会话过期后被删除。临时节点不是 TCP 断开即刻删除，中间存在检测和协商后的会话超时。

写入经 leader 协调并按协议提交，读可以由连接到的服务节点提供，可能落后于最新写入。不要概括为“任何客户端的任意读取都立即看到最新状态”。涉及新鲜度时结合 sync、版本和应用协议理解其保证。

ZooKeeper 写入依赖法定多数，三节点通常可容忍一个节点故障，五节点可容忍两个；增加节点可能提高读承载，但并不直接提高写性能。

## 2. Watch 与状态恢复

传统 watch 是一次性通知，触发后需要重新注册；还存在版本支持的持久 watch，使用时要明确客户端 API 和集群版本。通知表达“发生了变化”，不是完整事件日志，断连恢复时必须重新读取状态并重建本地视图。

连接状态至少区分暂时断连和会话过期。断连时不要继续假定自己拥有领导权；会话过期后旧临时节点和锁身份失效，需要新会话重新竞争。

## 3. 锁与选举的典型配方

```text
1. 在 /locks/order 下创建 EPHEMERAL_SEQUENTIAL 节点。
2. 获取子节点，按序号排序；自己最小则获得锁。
3. 否则只监听自己的前驱，减少惊群。
4. 前驱变化后重新查询并判断，处理“读取后前驱已消失”的竞态。
5. 会话失效立即失去身份；资源服务仍需 fencing 保护。
```

生产优先使用成熟配方库并理解其故障语义。创建节点后网络超时可能导致“已创建但未收到确认”，客户端需带可识别标记查找，避免无意生成多个候选节点。

## 4. 容量与排查

| 现象 | 重点检查 | 工程含义 |
| --- | --- | --- |
| 会话频繁过期 | GC 暂停、网络抖动、服务器延迟 | 不应只无限增大会话超时 |
| 写延迟升高 | 磁盘 fsync、法定多数、队列 | 事务日志磁盘与资源隔离很关键 |
| 节点/监听过多 | 客户端注册和清理路径 | 避免把高频业务实体逐个放进去 |
| 反复选主 | 网络分区、机器负载、日志 | 保留时间线，区分根因和后果 |

ACL 控制 znode 操作权限；网络可达并不意味着可开放匿名写入。备份必须覆盖可恢复的快照与事务日志组合，并实际验证恢复过程。

## 5. 面试与练习

- **临时节点能保证业务只有一个执行者吗？** 旧持有者暂停或失联后可能仍执行，需资源端 fencing 或原子业务约束。
- **为什么只监听前驱？** 降低一个锁释放导致所有等待者同时重试的放大效应。
- **练习**：三个竞争者选主，模拟断网、暂停、会话过期和恢复。验收：失效领导者不能写资源，候选节点不泄漏，恢复时通过读取重建状态而非依赖漏掉的通知。
