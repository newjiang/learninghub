# RocketMQ 业务消息导读与速查

> 阅读定位：本篇是导读与速查，不代替深入正文。已展开专题和当前覆盖边界见[知识手册导航](../../知识手册导航.md)。

基线：RocketMQ 5.x。SDK 类型与通信模型会影响 API，示例采用协议流程，实际工程按官方对应版本实现。

## 1. 消息模型与选型

生产者将消息发给 broker，topic 表示业务主题，队列提供并行基础；消费者组承担某类业务订阅。Tag 适合服务端过滤，不能作为用户权限隔离机制。普通消息用于解耦，FIFO 用于指定消息组的有序场景，延时消息表达未来投递，事务消息协调本地事务与消息提交。

顺序通常只在指定消息组及配套生产消费约束下成立，不是整个 topic 的全局顺序。业务若跨多个来源写同一订单，仍需状态机和版本防护。

## 2. 事务消息解决的范围

```text
1. 生产者发送 half message，普通消费者暂不可见。
2. half message 确认后执行本地业务事务。
3. 生产者提交或回滚消息。
4. 若结果不明确，broker 发起事务回查。
5. 回查读取持久化业务状态，给出 commit/rollback/unknown。
```

它帮助解决本地生产事务与消息提交的一致性，不保证消费者数据库和生产者数据库同时提交，也不使消息消费天然只发生一次。回查不能只检查进程内标志；状态要与业务事务一起持久化。

回查超时、最大次数和保留窗口要与最长本地事务及恢复目标匹配。长时间 unknown 需要可观测、可人工处理，不能无期限隐藏。

## 3. 消费可靠性

只有业务持久化成功才确认消费，失败按协议进入重试。去重使用稳定 event_id 或业务操作 ID，并与本地业务写入原子提交。仅在 Redis 标记“消费过”再写数据库会产生标记成功而业务失败的窗口。

重试需要区分暂时故障和永久无效数据；永久失败进入死信或人工处理流程，保留原始事件、失败原因、版本与重放记录。死信不是自动恢复，必须有所有者、告警和处理时限。

## 4. 工作场景：订单超时关闭

延时消息触发时查询订单真实状态，只有仍待支付才尝试条件关闭；支付回调也必须通过合法状态迁移防止覆盖已关闭状态。消息晚到、重复或暂时不可用都可能发生，定时扫描补偿负责兜底。

不要把到达时间当作精确调度 SLA。按业务要求区分“到时尽量触发”和“严格截止判断”，截止条件应在执行时用可信时间和数据库状态判断。

## 5. 排障与面试

积压检查生产速率、可用队列、消费者执行时间、重试和热点消息组。扩容消费者前估算数据库容量，防止积压恢复时形成第二次事故。发送超时不能证明未发送，重发需保留同一业务事件身份。

- **事务消息与 outbox 怎么选？** 前者依赖 broker 协议和回查能力；后者通过数据库本地原子性及独立投递器实现，都会涉及重复、延迟和运维成本。
- **顺序消息失败怎么办？** 保序重试可能阻塞对应流；隔离或跳过要明确会不会破坏业务语义。
- **练习**：支付结果消息与延时关闭消息并发到达。验收：合法终态唯一、重复事件不重复退款、事务回查可从持久化状态恢复、补偿扫描可修复漏处理。
