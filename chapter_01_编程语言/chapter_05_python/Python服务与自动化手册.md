# Python 服务与自动化导读与速查

> 阅读定位：本篇是导读与速查，不代替深入正文。已展开专题和当前覆盖边界见[知识手册导航](../../知识手册导航.md)。

适用范围：CPython 3.11/3.12 的常规带 GIL 构建。自由线程构建及第三方扩展兼容性需要独立验证，不能套用本章线程结论。

## 1. 语言语义与资源生命周期

名称绑定对象，赋值不复制对象。可变默认参数在函数定义时创建，会在调用间共享；默认值用 None 后在函数内构造。迭代器按需生成元素，生成器减少峰值内存，但也把错误发生时间推迟到消费阶段。

```python
from collections.abc import Iterable
from decimal import Decimal

def total(prices: Iterable[str]) -> Decimal:
    return sum((Decimal(p) for p in prices), start=Decimal('0'))

assert total(['10.20', '3.30']) == Decimal('13.50')
```

上下文管理器 `with` 用于文件、锁和事务的确定性清理，不能依赖垃圾回收及时关闭连接。装饰器保留 `functools.wraps` 元数据；缓存装饰器要考虑上限、过期、可变参数和跨用户隔离。

## 2. 并发模型的选型

| 工作负载 | 常用方案 | 关键边界 |
| --- | --- | --- |
| 阻塞 I/O SDK | 线程池 | 限制线程数，超时不一定中止底层调用 |
| 大量可异步 I/O | asyncio | 库本身需要支持异步，阻塞调用会卡住事件循环 |
| Python CPU 计算 | 多进程或本地扩展 | 考虑序列化、进程内存及扩展是否释放 GIL |
| 长任务 | 外部任务队列 | 重试、幂等、任务租约和结果存储 |

GIL 不等于业务线程安全；检查后更新、跨 I/O 的读改写仍可能竞争。asyncio 的协作调度也会在 await 之间暴露共享状态。并发上限应由下游容量决定，而不是仅由协程创建成本决定。

## 3. 服务工程与边界

类型注解有利于静态检查和 IDE，但默认不会强制运行期验证。HTTP/消息入口验证 schema，内部使用明确的领域对象；异常分为可重试、业务拒绝和程序错误，日志保留追踪 ID，避免记录密钥及完整个人信息。

依赖隔离用虚拟环境，声明直接依赖并锁定可重现的解析结果。构建与运行使用匹配的解释器和操作系统；含原生扩展的 wheel 需要验证平台。数据库连接按请求/事务边界管理，不要为每条 SQL 创建整个连接池。

## 4. 故障排查

延迟上升先分解排队、数据库、外部请求与计算；CPU 高用采样分析确认热点。内存增长区分对象保留和本地扩展分配：`tracemalloc` 能观察 Python 层分配，但不能解释所有进程 RSS。异步服务“吞吐低且 CPU 低”，检查同步客户端和连接池等待，再检查事件循环延迟。

超时后的重试必须使用总截止时间、有限次数、指数退避与抖动。支付等写操作只有在业务幂等且能查询原请求结果时才适合自动重试。

## 5. 面试追问与回答要点

- **列表推导式一定比生成器好吗？** 列表适合重复访问与已知小规模数据；生成器适合流式消费，需说明一次性迭代特征。
- **线程为什么还能加速？** 等待 I/O 时可能释放 GIL；某些本地扩展计算也会释放。不能推广为所有 Python CPU 代码。
- **asyncio 取消是否立刻停止？** 取消通常通过协作式异常传播，需要 finally 清理；底层阻塞操作和外部写入未必停止。

## 6. 练习与验收

编写分页同步程序：最多 5 个请求并发，单请求与总任务都设超时，失败页可续跑，目标表用业务唯一键去重。验收：中断重启不重复产生业务副作用；错误页有明确原因；百万行输入不需要一次全部加载内存。
